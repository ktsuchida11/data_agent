# ADR-0032: 用途パックで、土台と用途を分ける。ツールは「扱い」と一緒に登録し、守りはどのツールにも効かせる

- **状態:** 採用（実装済み）。オーナーが決めた（2026-11-17。「おすすめの方法で対応をおねがいします。ガードレールの汎用化と、ツール追加を容易にする、MCP サーバを追加できるようにする」）
- **日付:** 2026-11-17
- **決定者:** プロジェクトオーナー
- **対象:** data_agent

## 状況

- オーナーは、data_agent を、ほかの用途のチャットエージェントの土台にしたい。
- 守り（ガードレール、確認、回数の上限、監査ログ、コードを実行する専用のコンテナ）と、運用（会話の保存、定時実行、スキル、Langfuse）と、確かめる仕組み（単体テスト、画面の回帰確認、本物のモデルでの点検）は、用途に関係なく使える。
- 一方で、次のものがデータ分析に固有で、コードのあちこちに書かれていた。
  - **役割の文:** `src/data_agent/prompts/SYSTEM.md` と、画面の最初のあいさつ。
  - **ツール:** `agent.py` に、名前を書いて足していた。
  - **ツールの扱い:** 確認・回数の上限・照合が、ツールの名前ごとにコードに書かれていた。
- **ツールを 1 つ足すと、5〜6 か所を直す必要があった。** 直す場所は、`agent.py` のツールの一覧、確認の一覧、「毎回確認」の一覧、回数の上限、`security.yaml`、照合の対象、確認の画面の名前、回帰確認です。
- **守りの一部が、Web 検索の専用だった。** 送る内容に外に出したくない情報らしいものがないかの判定（ADR-0022）が、それに当たります。
- **ガードレールの検出ルールは、決まった種類だけだった。** 用途ごとの番号（社員番号など）を足せなかった。

## 決定

1. **用途ごとに違うものを、用途パック（`packs/<名前>/`）にまとめる。** どのパックを使うかは、`.env` の `AGENT_PACK` で選ぶ（既定は `data`）。
   - **`pack.yaml`:** 用途の名前、最初のあいさつ、役割の文のファイル、使う組み込みのツール、Python で書いたツールのファイル、MCP サーバー（ADR-0033）を書く。
   - **`SYSTEM.md`:** 役割の文。
   - **`tools.py`（任意）:** Python で書いたツール。
   - **書き間違い:** `pack.yaml` に知らない項目があれば、起動を止める。ファイルは、パックのフォルダの外を指せない。
   - **守りの設定:** `config/security.yaml` に残す。どのパックにも共通の守りにするため。
   - **これまでのデータ分析:** `packs/data/` に移した。中身と動きは変えていない（役割の文は、場所を移しただけ）。
2. **動いている 1 つのアプリは、1 つのパックで動かす。** 用途を 2 つ同時に使うときは、アプリを 2 つ動かす（作業フォルダ・長期メモ・スキルも、アプリごとに分かれる）。
3. **ツールは、扱い（`ToolPolicy`）と一緒に登録する（`tools/registry.py`）。** 次のものは、扱いから自動で決まる。
   - 実行の前に利用者に確かめるか（`require_approval`: `true`・`auto`・`false`）
   - 「毎回確認」のチャットで確かめるか（`strict`）
   - 送る前に引数を確かめるか（`check_arguments`）
   - 1 回の依頼で呼べる回数（`max_calls_per_run`）
   - 返事の照合で、根拠のデータとして扱うか（`grounding`）
   - 確認の画面や、定時実行の説明に出す名前（`label`）
4. **ツールの種類は 3 つにする。**
   - 組み込み（`run_python`・`database`・`web_search`）: 扱いは `config/security.yaml` から作る。前と同じ確認・回数の上限になることを、テストで確かめる。
   - Python で書いたツール: パックの `tools.py` に、`@agent_tool(label=…)` を付けた関数を書く。関数の名前がツールの名前、docstring がモデルへの説明になる。関数の中のエラーは、種類だけをモデルに返す（接続先や鍵が、エラーの文に入るため）。
   - MCP サーバーのツール: パックの `pack.yaml` に書く（ADR-0033）。
5. **ツールの名前を確かめる。** Deep Agents が元から持つツール（`read_file`・`write_file`・`task` など）と同じ名前は使えない。名前が重なっていれば、起動を止める。中身をすり替えさせないため。
6. **ガードレールを、どのツールにも効かせる（汎用化）。**
   - **ツールの結果のマスク:** もともと、どのツールの結果にも効いていた。パックのツールにも効くことを、テストで確かめる。
   - **送る前の引数の確かめ（新しく足した）:** `check_arguments` のツールは、引数に秘密情報や個人情報（ガードレールで「マスク」にしている種類）があれば、送らずに止める。監査ログには、ツールの名前と種類だけを残す。
     - 既定は、Python で書いたツールと MCP のツールで「確かめる」、組み込みで「確かめない」。Web 検索は、ツールの中で確かめていた。
   - **送る内容の判定（ADR-0022）を、Web 検索のほかのツールにも使えるようにした:** 扱いで `require_approval: auto` としたツールは、引数を同じ決まりで調べる。このチャットで読んだデータの写しや、見張る言葉が見つかれば、送る前に確かめる。
   - **独自の検出ルール（新しく足した）:** `config/security.yaml` の `guardrails.custom_rules` に、用途ごとの番号（社員番号、案件のコードなど）を正規表現で書き足せる。
     - 書いた正規表現は、起動の前に確かめる。読めない正規表現、空の文字列に一致するもの、元からある種類と同じ名前は、受け付けない。
7. **見本のパック `packs/internal_api_example/` を置く。** 社内の受注システム（の見本）を、MCP と Python のツールで使う例。チュートリアル（`docs/tutorials/`）で使う。
   - **→ 2026-11-17:** 見本の Python のツールを、社内 API を呼ばない計算（税込みの金額、`price_with_tax`）に替えた。社内の API は MCP でつなぐ（ADR-0033 の決定 9 を取りやめた）。

## 検討した案

| 案 | 内容 | 判断 |
|---|---|---|
| A. 用途ごとにリポジトリを写す | 写したものを、用途ごとに直す | 不採用。始めるのは簡単だが、守りを直すたびに、写したすべてに同じ修正が要る |
| **B. 1 つのリポジトリで、用途パックを切り替える** | 用途ごとに違うものだけをパックに書く | **採用**。守りの修正が、1 か所ですべての用途に効く |
| C. 土台をライブラリにして、用途ごとに別のリポジトリから使う | 土台を pip で入れる | 不採用。いまは用途が 2 つしかなく、版の管理の手間に見合わない。用途が増えたら考え直す |
| D. 1 つのアプリで、チャットごとに用途を切り替える | 画面で用途を選ぶ | 不採用。作業フォルダ・長期メモ・スキルが用途の間で混ざる。確認の決まりも混ざる |

## 確かめたこと（2026-11-17）

- **単体テスト:** 544 件すべて通った（新しく 59 件。`tests/test_tool_registry.py`、`tests/test_mcp.py`、`tests/test_prompts.py` の、パックごとの役割の文）。
  - **パック:** 読み込める。知らない項目、ないファイル、パックの外を指すファイル、ない名前のパックは、どこが違うかを書いて止める。
  - **組み込みのツール:** 扱いから作った確認・「毎回確認」・回数の上限が、パックを入れる前と同じになる。
  - **`@agent_tool`:** ツールの名前、説明、引数の説明を作る。エラーの文（接続先）は、モデルに渡らない。元からあるツールの名前と、説明のない関数は、受け付けない。
  - **ガードレール:** 独自のルールでマスクする。誤ったルールは受け付けない。送る前の確かめで、鍵とメールアドレスを含む引数は送らない。監査ログに値は残らない。
  - **確認:** パックのツールの確認に、`label` と引数が出る。定時実行の説明にも出る。送る内容の判定は、読んだデータの写しを、パックのツールに書いたときにも止める。
  - **確かめるコマンド:** `python -m data_agent.tools.registry`（パックの中身）と `python -m data_agent.safety.guardrails`（文章をガードレールに通す）。`python -m` で動かしたときに、モジュールが 2 回読み込まれてパックのツールを見落とす誤りを見つけて直した。

  - 独自のルールを足して試す、誤ったルールの知らせ。

  - Python のツールのテストのひな形。

## 分かっている制約

- **作業フォルダ・長期メモ・スキルは、パックごとではなく、アプリごと。** 用途を同時に 2 つ使うときは、アプリを 2 つ動かす。
- **点検（`evals/redteam`、`evals/factcheck`）の問題集は、データ分析のパック向け。** ほかのパックを本物のモデルで点検するときは、問題集を足す。
- **画面の名前（`.chainlit/config.toml` の `name`、`chainlit.md`）は、パックで変わらない。** いまは「データ分析エージェント」のまま。パックごとに変えるかは、使ってから決める。
- **パッケージの名前は `data_agent` のまま。** データベースとロールの名前（`coding_agent` など）も変えていない（ADR-0029）。
- **Python で書いたツールは、アプリと同じ権限で動く。** 環境変数（鍵）にも、ネットワークにも届く。アプリのコードと同じように中身を確かめてから足す。鍵は、コードに書かずに `.env` から読む。
- **送る前の確かめが見つけられるのは、形が決まった情報だけ（鍵、メールアドレス、電話番号など）。** 顧客の名前のようなものは、`require_approval: auto`（見張る言葉）か `true` で守る。
- **回数の上限は、実行の直前に数える。** 確認が要るツールでは、上限を超える回も確認が出る。承認したあとで止まる。
