# ADR-0028: コードを役割ごとのフォルダに分け、重なっている処理をまとめる

- **状態:** 採用（実装済み）。`prompts/`（役割の文）は、2026-11-17 に用途パック `packs/data/` へ移した（→ ADR-0032）。オーナーが決めた（2026-11-16。提案した案 A・B・C・D のすべてと、`customer_needs_agent/` を別のフォルダに移すこと）
- **日付:** 2026-11-16
- **決定者:** プロジェクトオーナー
- **対象:** data_agent（と、`LangChain/` の下のフォルダの置き方）

## 状況

- オーナーから、次の声があった（2026-11-16）。
  - 「Coding_agent と Customer_need_agent に分かれていて、どっちが動いているかもわかりにくい」
  - 「内容の割にファイルが多くて、とっても分かりにくい。リファクタリングもした方が良さそう」
- 調べて分かったこと:
  - **全体の地図がなかった。** README の構成の表は、ファイルを 1 つずつ並べていたが、1 回の依頼がどう流れるかは、どこにも書いていなかった。
  - **動いていないフォルダが並んでいた。** `customer_needs_agent/` は、2026-10-30 に設計書と一緒に作った叩き台で、一度も動かしていない。data_agent とは、コードもデータベースも共有していない。
  - **`src/data_agent/` に 20 個のファイルが平らに並んでいた。** 道具・守り・保存・機能の区別が、ファイル名からしか分からなかった。
  - **同じ処理が 2 か所にあった。**
    - 作り話の点検（factcheck）は、乗っ取りの点検（redteam）の内側の部品を借りて動き、実行の処理の多くを写していた。
    - 見張る言葉の一覧を作る処理は、判定のファイル（`search_screen.py`）・データベースのファイル（`database.py`）・組み立てのファイル（`agent.py`）の 3 か所に分かれていた。データベースのファイルは、そのために判定のファイルを読み込んでいた。
- ファイルの数そのものは、ほとんどが必要な役割を持っていた。消すと壊れるものもあった（下の「しなかったこと」）。

## 決定

1. **仕組みの説明書を作る**（`docs/architecture.md`）。動いているもの、1 回の依頼の流れ、守りの一覧、ファイルの地図を、1 か所にまとめる。README の構成の表は、フォルダ単位の短いものにして、細かい地図は説明書に一本化する。
2. **動いていないものを `LangChain/archive/` に移す。** `customer_needs_agent/` と、その設計書（`02_顧客ニーズ調査エージェント設計書.md`）。消さずに残す。
3. **`src/data_agent/` を、役割ごとのフォルダに分ける（案 D）。**

   | フォルダ | 中身 |
   |---|---|
   | `ui/` | 画面（いままでどおり） |
   | `tools/` | `code_execution.py`、`database.py`、`web_search.py`、`outputs.py` |
   | `safety/` | `approvals.py`、`limits.py`、`guardrails.py`、`guard_middleware.py`、`search_screen.py`、`watch_terms.py`（新しい）、`grounding.py`、`audit.py` |
   | `storage/` | `persistence.py`、`chat_history.py`、`tracing.py` |
   | `features/` | `schedules.py`、`schedule_runner.py`、`skill_mining.py` |
   | `evals/` | `redteam/`、`factcheck/`、`common.py`（新しい） |

   - `agent.py`・`settings.py`・`prompts/` は、動かさない。ファイルの場所をもとに動いているため（プロジェクトの場所の計算、プロンプトの読み込み、`agent.py` を文字として読むテスト、Dockerfile の起動のコマンド）。
   - 各フォルダの `__init__.py` の先頭に、中のファイルの役割を書く。
4. **点検の重なりをまとめる（案 A）。** 2 つの点検で共通の部品を `evals/common.py` に移す。モデルに見せるもの（プロンプト、道具の名前・説明・形、代わりの役の返事）は変えない。変えると、これまでの測定の結果と比べられなくなるため。
5. **見張る言葉の一覧を作る処理を 1 つにまとめる（案 B）。** `safety/watch_terms.py` に集める。質問文を調べる処理は、`search_screen.py` に残す。
6. **小さな掃除（案 C）。**
   - 画面のコマンドで重なっていた部品（利用者の ID、ボタンの対象の取り出し）を、`ui/chat_commands.py` の共通の部品にする。
   - 画面に付ける HTTP ヘッダーを、`ui/app.py` から `ui/connection_guard.py` に移す（入口の守りを 1 つのファイルに）。
   - 返事の照合の根拠の集め方を、`grounding.review()` の中に 1 つにする（画面と定時実行で、別々に書いていた）。
   - 使っていないコード（型の別名 1 つ、使っていない値 1 つ、使っていない読み込み 1 つ）を消す。
   - テスト: `test_permissions.py` を `test_approvals.py` にまとめる（同じ読み込み方を使っていた）。偽のモデルの名前の重なりを直す。回帰確認（`regress.sh`）から漏れていた、コードを実行する箱の確認（`check_sandbox.py`）を足す。
7. **過去の ADR は、ファイルの場所とコマンドだけを書き換える。** 決めた内容には触れない。リンクが切れると、オーナーが追えなくなるため。

## 検討した案

| 案 | 内容 | 効果 | 危なさ | 判断 |
|---|---|---|---|---|
| A. 点検の重なり | 共通の部品を 1 つのファイルに | 大（重なりがなくなる） | 中（モデルに見せるものを変えると、測り直しが要る） | **採用** |
| B. 見張る言葉 | 3 か所の処理を 1 つのファイルに | 中 | 小 | **採用** |
| C. 小さな掃除 | 重なった部品・使っていないコード | 小 | 小 | **採用** |
| D. フォルダ分け | 20 個のファイルを役割ごとのフォルダに | 中（ファイル名を見なくても役割が分かる） | 大（約 100 か所の読み込みと、過去の ADR のリンク 19 本、点検のコマンドが変わる） | **採用**（オーナー。勧めたのは A〜C だけだった） |

### しなかったこと

- **画面の言葉の翻訳ファイル（`.chainlit/translations/` の 23 個）を消す:** Chainlit は、起動のたびに、ないものを作り直そうとする。コンテナの中は書き込めないので、起動が止まるおそれがある。
- **`chainlit.md` を消す:** 同じ理由で必要。
- **`ui/app.py` を、さらに分ける:** 画面の状態を共有しているうえ、Chainlit の読み込み方の癖（ADR-0026 の追記の前の不具合）があり、ファイルが増えるだけになる。
- **2 つの点検の判定（`judge.py`）をまとめる:** 判定の決まりの作りが違い、共通の部分がほとんどない。
- **`scripts/setup_data_db.sh` を分ける:** 長さの多くは SQL と、それを説明する確認で、並べて置くほうが読みやすい。回帰確認が毎回使っている。

## 変わること

- **点検のコマンド:**

  | これまで | これから |
  |---|---|
  | `python -m coding_agent.redteam` | `python -m data_agent.evals.redteam` |
  | `python -m coding_agent.factcheck` | `python -m data_agent.evals.factcheck` |
  | `python -m coding_agent.schedule_runner` | `python -m data_agent.features.schedule_runner`（AWS で外から起動するとき） |

- **アプリのログの名前:** `schedule_runner` と `skill_mining` のログの名前（ログの行の頭に出るもの）が、`data_agent.features.…` に変わる。監査ログ（`"log": "audit"` の行）の名前と中身は変わらない。
- **保存した会話:** そのまま読める。会話の状態には、文字と数しか入っていない（ファイルの場所は入っていない）ことを確かめた。
- **動いているアプリ:** `docker compose up --build` で作り直すまでは、古いコードのまま動く。

## 確かめたこと（2026-11-16）

- **点検の自己点検（偽のモデル。料金なし）:** 動かす前に結果を取っておき、動かしたあとと比べた。乗っ取りの点検も、作り話の点検も、出力が 1 文字も変わらなかった。
- **単体テスト:** すべて通った（件数は、下の「結果」）。
- **画面の回帰確認:** `bash tests/e2e/regress.sh`（下の「結果」）。
- **リンク:** README・AGENTS.md・説明書・ADR の中のリンクの行き先が、すべてあることを確かめた（切れたリンク 0 本）。

### 結果

- **点検の自己点検:** 乗っ取りの点検も作り話の点検も、動かす前（基準）と、フォルダ分けのあと、共通の部品にまとめたあとの 3 回で、出力が 1 文字も変わらなかった。点検の問題の一覧（攻撃と質問の文字列。乗っ取り 286 個、作り話 105 個）も、変わっていないことを確かめた。
- **単体テスト:** 463 件すべて通った。足したもの: `tests/test_ui_helpers.py`（画面の共通の部品。3 件）、`tests/test_grounding.py`（照合の根拠の集め方。1 件）。`test_permissions.py` の分は、`test_approvals.py` に移した（件数は同じ）。
- **画面の回帰確認:** 17 種類、356 項目がすべて通った（`logs/e2e/20261116-100501`。新しく入れたコード実行の箱の確認 28 項目を含む）。
- **1 回目の回帰確認で見つかった誤り:** 画面の共通の部品（利用者の ID を返すもの）が、書き換えの誤りで、自分自身を呼び続けていた。画面のコマンドとチャットの開始が、すべて止まっていた（14 種類が失敗）。単体テストでは、この部品を試していなかったので気づけなかった。直して、部品の単体テスト（`tests/test_ui_helpers.py`）を足した。誤りを戻すと、そのテストが失敗することも確かめた。
- **数の変化（`src/data_agent/` の Python のファイル）:**

  | | 前 | 後 |
  |---|---|---|
  | `src/data_agent/` の直下 | 20 個のファイル | 3 個のファイルと 7 個のフォルダ |
  | ファイルの数（全体） | 35 | 42（各フォルダの説明の `__init__.py` が 5 個、`watch_terms.py`、`evals/common.py`） |
  | 行の数（全体） | 8,755 | 8,914（+159） |

  - 行が増えたのは、各フォルダの説明と、共通の部品の説明・引数のため。点検の 2 つのフォルダは、合わせて 2,609 行から 2,694 行（共通の部品を含む）になった。重なりはなくなったが、行は減っていない。
  - 作り話の点検が、乗っ取りの点検の内側の部品を借りることは、なくなった（どちらも `evals/common.py` を使う）。
