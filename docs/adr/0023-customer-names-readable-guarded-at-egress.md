# ADR-0023: 顧客の名前は、エージェントも読める。外に出る経路（Web 検索）で止める

- **状態:** 採用（実装済み）。オーナーが決めた（2026-11-15）。ADR-0019 の一部（練習用のデータで氏名を読めなくしたこと、下書きで人の名前らしい列を読めなくする既定）を置き換える
- **日付:** 2026-11-15
- **決定者:** プロジェクトオーナー
- **対象:** data_agent

## 状況

- ADR-0019 では、個人情報の列を、エージェントのロールから読めなくしました。練習用のデータでは、顧客の氏名（`customers.name`）とメールアドレス（`customers.email`）です。`--columns` が作る下書きも、人の名前らしい列を読めなくする既定でした。
- ADR-0022 で、Web 検索の前に、質問文に顧客の名前などがないかを調べる仕組みを作りました。名前は、そのための専用のロール（`coding_agent_screener`）だけが読んでいました。
- 2026-11-15 に、オーナーから次の要望がありました。「データベースから顧客の名前を読むことはできる必要があります。メールアドレスや、電話番号や名前などが Web 検索したり、インターネットの外に出力されることを懸念されています」。
- 確かめたところ、外（インターネット）に出る経路は、次の 2 つです。
  - **モデルの API（Anthropic）:** 会話と、ツールの結果が送られる。
  - **Web 検索:** 質問文が、検索のために外部に送られる。
- トレース（Langfuse）は手元で動いています。コードを実行するコンテナは、外へ出る経路のないネットワーク（`internal: true`）にあります。

## 決定

1. **エージェントは、顧客の名前を読めるようにします。** 名前を使う業務（一覧、宛名、集計の表など）のためです。
   - 練習用のデータでは、`customers.name` を、読めなくする列の一覧から外しました（`config/hidden_columns.coding_agent_sample.txt`）。
   - `--columns` が作る下書きでは、人の名前らしい列を、読める側（先頭に `#`）にしました。同時に、見張る列の下書き（`config/watch_columns.<名前>.txt`）を作り、そこに人の名前らしい列を入れます。名前の列らしいもの（会社名、商品名など）は、「？」を付けて候補に出します。
2. **メールアドレス・電話番号（と、住所など、ほかの個人情報らしい列）は、これまでどおり読めません**（列ごとの権限。ADR-0019）。読めなくし忘れた値は、モデルに渡る前と保存する前にマスクします。
3. **Web 検索の質問文に顧客の名前があれば、検索の前に確かめます。** 承認すれば検索します（オーナーの決定）。次のどちらの場合も確かめます（ADR-0022）。
   - モデルが、問い合わせで読んだ名前を書いたとき（手元のデータの写し）。
   - 利用者が自分で書いたとき（見張る言葉）。
4. **Web 検索の質問文にメールアドレスや電話番号があれば、断ります。** 承認しても検索しません（オーナーの決定。これまでどおり）。

## 外に出る経路と、名前の扱い

| 経路 | 顧客の名前 | メールアドレス・電話番号 |
|---|---|---|
| モデルの API（Anthropic） | 送られる（問い合わせの結果と会話） | 送られない（列で読めない。読めなくし忘れたものはマスク） |
| Web 検索 | 確かめる（承認したときだけ送る） | 断る |
| 会話の保存（手元の PostgreSQL） | 残る | マスクした形で残る |
| トレース（手元の Langfuse） | 残る | マスクした形で残る |
| 作業フォルダの CSV | 残る | マスクした形で残る |
| コードを実行するコンテナ | CSV で渡せる | マスクした形で渡る |

コードを実行するコンテナからは、外へ出られません（ADR-0016）。

## 検討した案

| 案 | 内容 | 良い点 | 困る点 |
|---|---|---|---|
| A. 読めないまま（ADR-0019 のまま） | エージェントは名前を読めない | 名前がモデルの API にも送られない | 名前を使う業務ができない |
| **B. 読める。Web 検索では確かめる（採用）** | 名前を読める。検索に入っていたら確認を出す | 名前を使う業務ができる。顧客と同じ名前の公人や会社も、承認すれば検索できる | 承認を押し間違えると、名前が外に出る。名前はモデルの API に送られる |
| C. 読める。Web 検索では断る | 名前を読める。検索に入っていたら、承認しても検索しない | 名前が検索で外に出ることはない | 顧客と同じ名前の公人や会社を、名前のままでは検索できない |
| D. 仮名にしてモデルに渡す | 名前を記号に置き換えて渡し、画面に出すときに戻す | 名前がモデルの API にも送られない | 名前を見つける仕組みが要る（列で決めても、文章の中の名前は難しい）。宛名づくりなどがしにくい。作るのに手間がかかる |

オーナーは、B を選びました（2026-11-15。C との比較を示して確かめた）。

## 確かめたこと（2026-11-15）

**データベースの準備のスクリプト（使い捨ての `postgres:17`）**
- 練習用のデータで、エージェントのロールは `customers.name` を読め、`email` は読めない。
- 本番を想定した表（氏名、メールアドレス、電話番号、住所、地域の列がある顧客の表、会社の表、商品の表）で、`--columns` が作る下書きを確かめた。
  - 読めなくする列の下書き: 氏名は読める側（先頭に `#`）、メールアドレス・電話番号・住所は読めない側になった。
  - 見張る列の下書き: 氏名が入り、会社名と商品名は「？」付きの候補になった。
- 会社名の行を有効にして適用した。
  - エージェントのロールは、氏名・会社名・地域・商品名を読め、メールアドレス・電話番号・住所は読めなかった。
  - 見張る用のロールは、氏名と会社名だけを読めた。
  - アプリは、日本語の氏名、英語の氏名（`John Smith`）、会社名（「株式会社」を除いた形も）を見張れた。

**アプリとつないだ確認（偽のモデル。`tests/e2e/check_database.py`。画面と同じ通信）**
- 直接呼ぶ確認 54 件、チャットでの確認 25 件が、すべて通った。
- 顧客の名前は、問い合わせで取れる。メールアドレスを使う問い合わせは、どの書き方（列、`SELECT *`、式、条件、行の全体、副問い合わせ）でも断られる。
- 問い合わせで読んだ顧客の名前を、モデルが自分から検索に書こうとすると、確かめられる。拒否すると検索しない。
- 利用者が顧客の名前を書いた検索は、確かめられる。名字だけなら、確かめずに検索する。

**本物のモデル（ADR-0022 に記録）**
- 名前を読めなくしていたときに試した（2026-11-15）。
  - モデル自身が、データベースの内容を検索に書かなかった（エージェントへの指示）。
  - 顧客と同じ名前の公人を調べる検索では、確認の画面が出た。

## 分かっている制約

- **顧客の名前は、モデルの API（Anthropic）に送られます。** 会話の履歴（手元の PostgreSQL）とトレース（手元の Langfuse）にも残ります。
- **確認で承認すれば、名前は Web 検索で外に出ます。** 押し間違えを防ぐ仕組みは、確認の画面（何が見つかったかを出す）と、「以後確認しない」を出さないことだけです。
- **見張る列に入れていない名前は、写しの判定だけになります。** 写しの判定は、4 文字以上の表の値と、10 文字以上続いた文です。カタカナだけの名前と、英語の名前（小文字の語）は、写しとしては見つけません。名前の列は、必ず見張る列の一覧にも書いてください（下書きには入れてある）。
- **言い換えた名前は、見つけられません。** 名字だけ、名前だけ、ふりがな、ローマ字です（ADR-0022）。
- **住所・生年月日などの列は、下書きでは読めないままです。** 読ませるかどうかは、列ごとに決めます。

## 見直す条件

- 顧客の名前を外部のモデルに送ってはいけない取り決め（契約や社内の規程）があると分かったとき。案 D（仮名）か、案 A に戻す。
- 承認の押し間違えで、名前が外に出たとき。案 C（名前は断る）に切り替える。
- 本番のデータベースで、名前の列が見張る列の一覧から漏れていたと分かったとき。
