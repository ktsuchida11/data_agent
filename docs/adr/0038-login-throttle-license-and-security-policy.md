# ADR-0038: 公開に向けて、ログインの失敗の回数を制限し、MIT ライセンスと SECURITY.md を置く

- **状態:** 採用（実装済み）。オーナーが決めた（2026-11-18。「MITで、ADRも入れて、１だけで良いです、あとはライセンスとSECURITY.mdを追加して終わりで良いです。」。「１」は、提案した進め方の 1 番目「ログインの失敗の制限を入れる」）
- **日付:** 2026-11-18
- **決定者:** プロジェクトオーナー
- **対象:** data_agent

## 状況

- オーナーは、このリポジトリを公開して、ハンズオンで使いたい（「これをパブリックに公開してハンズオンで使いたいのですが、セキュリティ周り調べてください」）。
- 調べた結果（2026-11-18）:
  - 本物の鍵と個人情報は入っていない。依存ライブラリにも、既知の脆弱性はなかった（毎日の点検）。
  - 直していない弱点が、資料に書いてあった。コードを実行する環境（sandbox）からアプリのログインの入口に届くので、仕込まれたコードがパスワードを総当たりで試せる（ADR-0034 の「判断待ち」）。公開すると、攻め方の手がかりを配ることになる。
  - ライセンスがなかった。ないと、参加者は写して変える許可がない。
- 調べた結果のうち、公開用のリポジトリを別に作ること（履歴の会社のメールアドレス、手元の事情の書き換え、参加者向けの構成）と、GitHub の設定は、今回はしない（オーナーの判断）。

## 決定

1. **ログインの失敗の回数を、接続元ごとに制限する**（ADR-0034 で示した案 (1)）。`src/data_agent/ui/login_guard.py`。
   - 続けて 5 回まで試せる。使い切ると 60 秒受け付けず（HTTP 429。待つ秒数は `Retry-After`）、そのあとも試すたびに倍にする（上限 15 分）。成功したら数え直す。1 時間試さなければ、数え直す。
   - 試した回数は、答えを待たずに、受け付けた時点で数える。同時にたくさん送られても、5 回を超えては通らない。
   - 接続元は、つないできた相手のアドレス。`X-Forwarded-For` は見ない（仕込まれたコードが自由に書けるので、信じると接続元を偽れる）。
   - 接続元ごとに数えるので、仕込まれたコードが失敗を重ねても、画面を開いている利用者は締め出されない。
   - 失敗して受け付けなくなったときに、監査ログに `login_throttled` を 1 回だけ書く（429 のたびには書かない。総当たりで、監査ログを埋めさせない）。（→ 2026-11-19 に、最初の 429 のときから、この時点に変えた。ADR-0039）
   - 設定は `config/security.yaml` の `login`。接続元の検査（ADR-0027）の内側に付ける（接続元で断った通信は数えない）。
2. **ライセンスは MIT にする**（`LICENSE`）。著作権者の欄は、公開する GitHub のアカウント名（`ktsuchida11`）にした。
3. **脆弱性の知らせ方と、分かっている制約を `SECURITY.md` に書く。** 公開の Issue には書かず、GitHub の非公開の報告（private vulnerability reporting）で知らせてもらう。分かっている制約（マスクの限界、ログインが 1 人分、など）と、使う人への注意（鍵は `.env` だけ、画面は手元だけ、使う金額の上限）も書く。英語の要約も付ける。
4. **ADR も、公開するリポジトリに入れる**（オーナーの決定）。決めた理由が学べるため。

## 検討した案

| 案 | 内容 | 判断 |
|---|---|---|
| **A. 接続元ごとに数え、待つ時間を倍にしていく** | 5 回まで、そのあと 1 分・2 分・4 分…（最大 15 分） | **採用**。総当たりは 1 日に 100 回ほどしか試せない。利用者は締め出されない |
| B. 名前（ユーザー名）ごとに数える | Chainlit のログインの部品は、接続元を渡さないので、こちらなら部品の中で数えられる | 不採用。利用者は 1 人なので、仕込まれたコードが失敗を重ねると、利用者が締め出される |
| C. コードを実行する環境を、画面と別のネットワークにする（ADR-0034 の案 (2)） | 届かないようにする | 今回は不採用。構成の変更になる。AWS に移すときに考える（ADR-0016） |
| D. 回数を数えず、毎回少し待たせる | 1 回ごとに 1 秒など | 不採用。同時にたくさん送られると、効かない |

- ライセンス: MIT（オーナーが選んだ）。ほかの候補は Apache-2.0（特許についての決まりを含む）だった。

## 確かめたこと（2026-11-18）

- **単体テスト:** `tests/test_login_guard.py`（16 件）。5 回目までは通り 6 回目から 429、待つ時間の倍増と上限、成功で数え直す、接続元ごとに数える、同時に 20 件送っても 5 件しか通らない、`X-Forwarded-For` を偽っても逃れられない、ほかの通信は数えない。全体で 604 件が通った。
- **画面と同じ通信（`regress.sh login`）:** コードを実行する環境にコードを送って総当たりを試すと、`[401, 401, 401, 401, 401, 429, 429, 429]` になった。そのあいだも、画面の利用者はログインできた。4 回間違えたあとの正しいパスワードは通り、使い切ったあとは正しいパスワードでも 429 になった。
- **全体の回帰確認:** `bash tests/e2e/regress.sh` で、全 19 種類・398 項目が通った（`logs/e2e/20261118-120153`）。ログインの入口の守りを足しても、ほかの確認（ログインを何度もするものを含む）は壊れていない。

## 分かっている制約

- **数はアプリのメモリにだけ持つ。** アプリを起動し直すと、数え直す。アプリを何台も並べると、台ごとに数える。
- **ロードバランサーの後ろ（AWS）では、すべての接続元が、ロードバランサーのアドレスに見える。** そのままだと、1 人の失敗で全員が待たされる。AWS に移すときに、どの接続元を信じるかを決めて直す。
- **画面のログインの欄には、待たされている理由は出ない。** Chainlit の画面は、ログインの失敗を、決まった言葉でしか表示しない。理由（日本語）は、応答の中身と監査ログにある。
- 公開用のリポジトリを別に作ることと、GitHub の設定は、していない。いまのリポジトリをそのまま公開すると、履歴（2026-11-18 からの記録）の作者のメールアドレスも見える。
