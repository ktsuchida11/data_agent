# ADR-0019: 個人情報は、データベースの列ごとの権限と、ガードレールのマスクで守る

- **状態:** 採用（実装済み）。一部置き換え済み（→ ADR-0023。顧客の名前は、エージェントも読めるようにした。2026-11-15）。「個人情報の列を、データベースの側で読めなくする」ことと、「メールアドレスと電話番号をマスクする」ことは、オーナーが決めた（2026-11-14）。次の点は、提案どおりに実装した。オーナーの確認はまだ取れていない: 口座番号のルールを足したこと、練習用ではないデータベースでは「読めなくする列の一覧」を必須にしたこと、ビューの扱い、読むデータベースの切り替え
- **日付:** 2026-11-14
- **決定者:** プロジェクトオーナー
- **対象:** data_agent

## 状況

- エージェントが読むデータベース（ADR-0017）には、個人情報を含む表があります（オーナー）。問い合わせの結果の先頭は、モデル（Anthropic の API）に送られ、会話の履歴にも残ります。
- それまでのガードレール（ADR-0012）は、氏名や住所を見つけられず、メールアドレスと電話番号は、見つけても記録するだけでした。
- オーナーから「法人で使うなら、ガードレールで守るものではないか」という指摘がありました。あわせて、オーナーが別のアプリで作ったガードレールの発表資料が示されました（`AIWorkshop202611` の `session4-45min.pptx`、2026-11-06）。

## 資料と見比べて分かったこと

資料に書かれていた問題が、このアプリにもあるかを、実際に試しました。

| 資料に書かれていたこと | このアプリで試した結果（直す前） | 対応 |
|---|---|---|
| 正規表現の `\b` は、日本語の隣では区切りにならない。検出率が 58.5% だった | **同じ問題があった。**「鍵はsk-…です」のように、日本語に続けて書いたキーを、6 例のうち 4 例見逃した | 秘密情報のルールを直した |
| 電話番号は、区切り方の違いで見逃す（30% → 直して 90%） | かっこ、空白、ピリオド、全角、区切りのない固定電話を見逃した（17 例のうち 10 例）。注文番号（0001-0002-0003）を、電話番号と間違えた | ルールを直し、桁数の確認を足した |
| 個人情報は、モデルに送る直前に、すべての呼び出しで置き換える（メール、カード番号、マイナンバー、電話、口座） | 入力・ツールの結果・返事の3か所で検査していた。メールと電話は記録だけで、口座のルールはなかった | メールと電話をマスクに変えた。口座番号のルールを足した |
| 氏名は対象にしない（自動で見つける方法は、公人の名前も消して、回答が壊れた） | 氏名は見つけられない | 自動の検出は足さない。データベースでは、列ごとに読めなくする |

## 決定

- **データベースの個人情報は、列ごとに読めなくします。** 読み取り専用のロール（ADR-0017）から、その列を読む権限を外します。データベースが断るので、SQL の書き方では回避できません。
- **メールアドレスと電話番号は、既定でマスクします。** データベースの結果だけでなく、利用者の入力、読んだファイル、モデルの返事にも効きます（ADR-0012 の「記録だけ」を変更）。
- **口座番号のルールを足します。**「口座」「普通」「当座」「預金」に続く 7 桁の数字です。
- **検出ルールは、日本語に続けて書かれたものと、全角・表記ゆれを見逃さない形に直します。**
- **氏名と住所を自動で見つける仕組みは、入れません。**

## 仕組み（列を読めなくする）

| 段階 | 内容 |
|---|---|
| **一覧の下書き** | `bash scripts/setup_data_db.sh --columns <名前>` が、表と列の名前を調べて、`config/hidden_columns.<名前>.txt` を作る。列の名前から個人情報らしいもの（メール、電話、住所、生年月日、氏名、パスワードなど）に印を付ける。データの中身は読まない |
| **確認** | 人が一覧を見て、足したり外したりする。1行に1つ、`表.列` と書く。`表.*` は表の全体 |
| **適用** | `bash scripts/setup_data_db.sh <名前>` が、一覧の列を除いた列だけを、ロールに許す。途中で失敗したら、全部をもとに戻す |
| **確認（自動）** | 適用のあと、その列が本当に読めなくなったかを、データベースに確かめる。ほかの経路（すべてのロールへの許可）で読めるなら、止めて知らせる |
| **エージェントから** | 表の一覧（`list_database_tables`）では、その列は「読めない」と出る。SQL に書くと、問い合わせの全体が断られ、理由がモデルに伝わる |

| ファイル | 役割 |
|---|---|
| `scripts/setup_data_db.sh` | 一覧の下書き（`--columns`）、権限の適用、適用後の確認、読むデータベースの切り替え |
| `config/hidden_columns.<名前>.txt` | 読めなくする列の一覧。練習用のデータ向けのもの（`coding_agent_sample`）は、メールアドレスを読めなくしてある（氏名は、2026-11-15 から読める。ADR-0023） |
| `src/data_agent/tools/database.py` | 表の一覧に「読めない」と出す。断られたときの説明 |
| `src/data_agent/safety/guardrails.py` | 検出ルール（日本語の隣、全角、表記ゆれ、口座番号） |

## 守りの重ね方

| 守り | 内容 |
|---|---|
| **列ごとの権限** | これが本当の守り。式の中、別名、条件（WHERE）、並べ替え、副問い合わせ、行の全体、`SELECT *`、COPY のどれでも読めない。統計情報（よく出る値の一覧）からも見えない |
| **ビュー** | ビューは、作った人の権限で中の表を読む。読めなくした列がある表を使うビューは、自動で読めなくする。集計だけのビューなど、読ませてよいものは、一覧に `+ビューの名前` と書く |
| **子の表** | パーティションの子の表も、同じ列を読めなくする |
| **書き間違いで止める** | 一覧に、ない表や列を書くと、適用せずに止まる（気づかないまま読める状態になるのを防ぐ） |
| **安全な側に倒す** | 練習用ではないデータベースは、一覧のファイルがなければ用意しない。読めない列がある表にあとから足した列は、用意し直すまで読めない |
| **マスク** | 読めなくし忘れた列に、メールアドレス・電話番号・口座番号・カード番号・マイナンバーが入っていたときの保険。モデルに渡る前と、CSV に保存する前に置き換える |
| **指示文** | 「読めない」とされた列や、マスクされた値を、別の方法で取り出そうとしないよう、モデルに伝えてある |

**追記（2026-11-15。ADR-0023）:** 顧客の名前は、エージェントも読めるようにしました（オーナーの決定）。練習用のデータでは、`customers.name` を読めなくする列の一覧から外し、`--columns` の下書きでも、人の名前らしい列は読める側にしました。名前は、Web 検索に入れようとすると確かめます（ADR-0022）。メールアドレスと電話番号は、これまでどおり読めず、検索も断ります。

**追記（2026-11-15。ADR-0022）:** Web 検索の前の確認で、顧客の名前を「見張る言葉」にするために、名前の列だけを読める別のロール（`coding_agent_screener`）を足しました（`config/watch_columns.<名前>.txt` に書いた列だけ。`scripts/setup_data_db.sh` が作る）。読むのはアプリで、値はアプリのメモリーの中だけで使い、モデルには渡しません。エージェントのロール（`coding_agent_reader`）とツールは、これまでどおり、読めなくした列を読めません。

## 検討した選択肢

| | A. 列ごとに読めなくする（採用） | B. A に加えて、氏名・住所の自動検出 | C. 自動検出だけ |
|---|---|---|---|
| **追加の料金** | なし | なし（自前で動かす場合） | なし（自前で動かす場合） |
| **確実さ** | 指定した列は、確実に読めない | A と同じ。指定し忘れた列の保険が増える | 見逃した氏名は、そのままモデルに送られる |
| **手間** | どの列が個人情報かを、一度決める | A と同じ | 指定は要らない |
| **副作用** | 読めなくした列は、条件や結合にも使えない | 人の名前ではない言葉（商品名、会社名、公人の名前）も消すことがある。アプリが大きく、遅くなる | B と同じ |

オーナーは A を選びました。B の「人の名前ではない言葉も消す」は、オーナーの資料にも結果があります（私人の氏名は 10 件すべて拾うが、公人の名前も 10 件のうち 5 件消した）。

## 確かめたこと（2026-11-14）

**検出ルール（単体テスト。`tests/test_guardrails.py`）**
- 日本語に続けて書いたキー 7 例、電話番号の書き方 20 例、メールアドレス・カード番号・マイナンバー・口座番号 10 例を、すべてマスクする。
- ふつうの数字 14 例（日付、注文番号、小数、社員番号、金額、郵便番号、集計結果の1行など）は、マスクしない。
- 件数は、自分で作った例の数です。大きなデータでの検出率と誤検知の率は、測っていません。

**準備用のスクリプト（77 項目。使い捨ての PostgreSQL 17）**
- 下書きに、メールアドレスの列と、その表の `name` が候補として入る。商品の `name` は候補にせず、確認を促す。
- 読めなくした列は、上の「列ごとの権限」に書いたどの書き方でも読めない（14 通り）。読める列、件数、集計、結合は使える。
- ビュー、ビューの上のビュー、行の全体を出すビュー、値を写したビュー（マテリアライズドビュー）は、読めなくなる。`+` を付けたビューは読める。
- ない表・ない列・引用符を含む行・書き方の違う行は、止まる。止まっても、前に読めなくした列は、読めないまま。
- 一覧から外すと読めるようになる。表の全体も読めなくできる。あとから足した列は、用意し直すまで読めない。
- すべてのロールへの許可（PUBLIC）があると、止まって知らせる。
- 別の名前で実行すると、読むデータベースが切り替わる。`.env` は名前の行だけが変わり、前のデータベースの表は読めなくなる。

**アプリとつないだ状態（偽のモデル。`tests/e2e/check_database.py` の `direct` 47 項目・`chat` 20 項目、`check_guardrails.py` 17 項目）**
- 表の一覧に「読めない」と出る。氏名とメールアドレスを問い合わせると断られ、値はモデルに渡らず、ファイルも作られない。
- 結果に出たメールアドレスと電話番号は、モデルに渡る前にも、保存した CSV でも、マスクされる。
- 利用者が入力したメールアドレスと、全角で書いた電話番号は、マスクされる。

**これまでの機能**
- 単体テストは 219 件すべて通った（165 件から、54 件を足した）。
- コードの実行、承認制、モデルの切り替え、定時実行、スキルの提案、アーカイブとグループ分け、過去のチャットの確認は、最終のイメージですべて通った。ログにエラーはなかった。

**確認していないこと**
- **本物のモデルでの動き。** 読めない列があるときに、モデルが列を書き直して問い合わせをやり直すか、利用者に「読めない設定です」と伝えるかは、使ってみないと分かりません。
- 練習用ではないデータベースでの動作。列の名前からの推測が、どのくらい当たるか。
- AWS の RDS（準備用のスクリプトは、手元の PostgreSQL のコンテナ向けです）。

## 分かっている制約

- **どの列が個人情報かは、人が決めます。** 下書きの印は、列の名前からの推測です。印のない列（備考など）に氏名や住所が書かれていれば、モデルに渡ります。
- **読めなくした列は、条件や結合にも使えません。** 結合に使う番号の列（ID）を読めなくすると、その表は集計に使えなくなります。
- **メールアドレスと電話番号のマスクは、アプリの全体に効きます。** 連絡先の一覧を作る、メールアドレスを含むファイルを編集する、といった作業はできなくなります（マスクされた値を含む書き込みは、拒否されます）。`config/security.yaml` で `log` に戻せます。
- **電話番号は、0 で始まる 10 桁の番号を広く拾います。** ゼロで埋めた 10 桁の番号（ID など）を、電話番号と間違えることがあります。
- **口座番号は、前に「口座」などの言葉があるものだけです。** 番号だけの列は、列ごとに読めなくしてください。
- **集計だけのビューも、いったん読めなくなります。** 行の全体を出すビューと見分けられないためです。読ませてよいものは、一覧に `+ビューの名前` と書きます。
- **関数（作った人の権限で動くもの）が個人情報を返す場合は、調べていません。**
- **表や列の名前に、ピリオド・カンマ・空白・引用符があるものは、一覧に書けません。**
- **読み取り専用のロールは、PostgreSQL の既定の設定では、同じサーバーのほかのデータベースに接続できます。** 表は読めませんが、表の名前は見えます。エージェントのツールは、設定されたデータベースにしかつなぎません（ADR-0017 の「ほかのデータベースにはつなげない」は、正確ではありませんでした）。
- **すでに画面の履歴に残っているメールアドレスなどは、さかのぼっては消えません。** モデルに送るときには、マスクされます。

## 見直す条件

- 氏名や住所が、自由記述の列に多く入っていると分かったとき（自動検出を足すかを決める）。
- メールアドレスや電話番号を扱う作業が必要になったとき（種類ごとの扱いを、場面で分けるかを決める）。
- 複数人で使うようになり、利用者ごとに読める列を分けたくなったとき。
