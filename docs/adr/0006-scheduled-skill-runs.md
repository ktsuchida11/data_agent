# ADR-0006: 指定した日時の実行は、アプリの中の見張りで行い、外からも起動できる形にする

- **状態:** 採用（実装済み）。オーナーは提案に変更を加えず、続行を指示した
- **日付:** 2026-11-13
- **決定者:** プロジェクトオーナー
- **対象:** data_agent

## 状況

cron のように、指定した日時に依頼やスキルを動かす機能がほしい、という要望があります。
例: 「平日の朝9時に、README を読んで今日やることをまとめる」。

最終的な実行環境は、自前で構成する AWS の ECS です（ADR-0009）。手元でも動かして確かめたい、という事情もあります。

## 決定

- **予定は「cron 式」と「依頼文」の組で登録します。** スキルを使わせたいときは、依頼文に「スキル ○○ を使って」と書きます。
- **登録・一覧・停止・削除は、チャットのコマンドで行います**（入力欄の `/`。ADR-0013）。
- **登録は承認制です。** 内容と、これからの実行時刻を見せて、ボタンで確かめてから登録します。
- **実行は、アプリの中の見張りが行います。** 一定の間隔で、時刻が来た予定がないかを見ます。
- **同じ処理を、外からも起動できるようにします。** AWS では、EventBridge Scheduler から ECS のタスクとして起動する形に替えられます。
- **無人で動くので、承認が必要な操作は自動で拒否します。** 対象は、ファイルの削除とメモリへの書き込みです。（設定でツールごとに確認つきにしたものと、既定を「毎回確認」にしたときの書き込み・実行・検索も、対象になる。ADR-0021）Web 検索は、2026-11-15 から、外に出したくない情報らしいものを含むときだけ確認するので、定時実行では、その検索だけを自動で拒否します（オーナーの決定。ADR-0022）。
- **実行の結果は、チャットとして残します。** 左の一覧の「定時実行」グループに出て、開いて続きを話せます。

## 仕組み

| 項目 | 内容 |
|---|---|
| **保存先** | 会話と同じデータベースの `Schedule` の表（ADR-0010）。会話を PostgreSQL に保存しているときだけ使える |
| **時刻の解釈** | `SCHEDULE_TIMEZONE`（既定は日本時間）。データベースには UTC で保存する |
| **見張りの間隔** | `SCHEDULER_POLL_SECONDS`（既定は 30 秒） |
| **使うモデル** | 登録したときに、そのチャットで選んでいたモデル |
| **外からの起動** | `python -m data_agent.features.schedule_runner`。時刻が来た予定を実行して終わる。この形にするときは、`SCHEDULER_ENABLED=false` でアプリの中の見張りを止める |
| **コード** | `schedules.py`（解釈と保存）、`schedule_runner.py`（実行）、`ui/schedule_commands.py`（コマンド） |

### コマンド

| コマンド | 動き |
|---|---|
| 定時実行 | 「分 時 日 月 曜日」の5項目と依頼文を書いて送る。例: `0 9 * * 1-5 README を読んで、今日やることを3行でまとめて` |
| 定時実行一覧 | 登録した予定を表示する。ボタンで、止める・再開する・削除する。前回の結果のチャットを開くリンクも出る |

### 守りと上限

- **二重に実行しない。** 予定の確保は「次の実行時刻を書き換えられたら勝ち」で決めます。アプリが複数動いていても、外からの起動と重なっても、同じ回を実行するのは1か所だけです。
- **止まっていた間の分は、1回だけ実行する。** アプリが止まっていた間に過ぎた回を、まとめて何度も実行することはありません。
- **上限がある。** 1人が登録できるのは 20 件まで、実行の間隔は 5 分以上です（`config/security.yaml` の `schedules`）。料金がかさむのを防ぐためです。
- **本人の予定だけを操作できる。** 停止と削除は、本人の予定だけを対象にします。
- **ガードレールと監査ログが効く。** 依頼文と返事はマスクされ、実行の開始と終了、自動で拒否した承認が監査ログに出ます（ADR-0012）。

## 検討した選択肢

| | A. アプリの中の見張り（採用） | B. Managed Deep Agents の schedules | C. OS の cron | D. EventBridge Scheduler + ECS タスク |
|---|---|---|---|---|
| **動く条件** | アプリが起動している間 | LangSmith Cloud 上で常に動く | Mac が起きている間 | AWS 上で常に動く |
| **手元で試せるか** | 試せる | 試せない | 試せる | 試せない |
| **最終的な環境で使えるか** | 使える | 使えない（Enterprise プランが必要） | 使えない | 使える |

A を採用し、実行の本体を D からも呼べる形にしました。手元では A で動かし、AWS では、起動する役だけを D に替えられます。

## 確かめたこと（2026-11-13）

使い捨ての PostgreSQL と偽のモデルを使い、画面と同じ通信で確かめました。実行の時刻は、データベースの「次の実行時刻」を過去に書き換えて、すぐに来たことにしています。

**確認できたこと**
- cron 式がない、間隔が短すぎる、読み取れない時刻、のそれぞれが理由付きで断られる。
- 確認のボタンで「やめる」を選ぶと登録されず、「登録する」を選ぶと登録される。
- 時刻が来ると実行され、結果が「定時実行」グループのチャットとして一覧に出る。
- 結果のチャットを開いて、続きを話せる（返事が「2通目」になる）。
- 同じ回を確保できるのは1か所だけである（アプリの見張りと、別の5つの確保を同時に走らせて確認）。
- ファイルの削除を頼む予定を実行すると、削除は自動で拒否され、ファイルは残る。
- ボタンで予定を止められ、止めた予定は時刻が来ても実行されない。ボタンで削除できる。
- 外から起動する形（`python -m data_agent.features.schedule_runner`）が動く。
- 前回までの機能（モデルの切り替え、ガードレール、一覧・再開・削除、アーカイブ・グループ分け）が、引き続き通る。
- 単体テスト 60 件が通る。

**確認していないこと**
- 本物のモデルでの実行。
- ブラウザの画面での見え方（確認のボタン、一覧のボタン、結果を開くリンク）。
- 本当に時刻が来るのを待っての実行。時刻の計算は単体テストで確かめています。
- AWS での、EventBridge からの起動。

## 分かっている制約

- **コードの実行はできません。** いまのエージェントはファイルの読み書きしかできないので（ADR-0002）、定時実行できるのも、それで完結する依頼だけです。
- **アプリが止まっている間は動きません**（アプリの中の見張りを使う場合）。
- **実行の途中でアプリが止まると、その回は「実行中」のまま残ります。** やり直しはしません。
- **時刻は cron 式で書く必要があります。** 「毎朝9時に」のような言葉での登録には対応していません。
- **予定の編集はできません。** 削除して、登録し直します。
- **タイムゾーンは全体で1つです。** 利用者ごとには変えられません。
