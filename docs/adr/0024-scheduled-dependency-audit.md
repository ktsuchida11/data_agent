# ADR-0024: 依存ライブラリの既知の脆弱性を、手元の Mac で週に1回（2026-11-16 に毎日に変えた）、自動で調べる

- **状態:** 採用（実装済み）。2026-11-16 に、オーナーが「毎日」に決めた（「依存ライブラリのチェックは毎日しないとですね」。下の「追記」）。オーナーが Mac に登録した（2026-11-17。1 回目の結果は「見つからなかった」。下の「追記」）。ADR-0020 の「依存ライブラリの確認を、定期的に行う方法を決める」への答え
- **日付:** 2026-11-15
- **決定者:** プロジェクトオーナー
- **対象:** data_agent

## 状況

- 依存ライブラリの既知の脆弱性は、2026-11-14 に `uv audit` で調べ、0 件でした（ADR-0020）。調べたのは、アプリのライブラリ（`uv.lock` の 174 個）と、コードを実行する環境のライブラリ（`sandbox/requirements.txt` の 28 個）です。
- 脆弱性は、ライブラリを変えなくても、あとから見つかります。調べた日に 0 件でも、翌週に見つかることがあります。そのため、ADR-0020 に「定期的に行う方法を決める」が残っていました。
- これまでの手順には、2 つの手間がありました。
  - `uv audit --frozen` は、アプリの分しか調べない。
  - コードを実行する環境の分は、版の一覧から仮のプロジェクトを作って調べる必要がある。
- このプロジェクトは Git のリポジトリになっていないので、GitHub の仕組み（Dependabot など）は、いまは使えません。
- オーナーは、料金のかからない、自前の構成を好みます。

## 決定（提案）

1. **2 つを一度に調べるスクリプトを作りました**（`scripts/audit_deps.sh`）。
   - 調べるのは、アプリのライブラリ（`uv.lock`）と、コードを実行する環境のライブラリ（`sandbox/requirements.txt`）。後者は、同じ版だけを使う仮のプロジェクトを作って調べる。
   - 結果は `logs/audit/<日時>.txt` に残る（イメージには入らない）。
   - 終了コードは、0 が見つからなかった、1 が見つかった、2 が調べられなかった（ネットワークなど）。
   - 調べる先は OSV（`api.osv.dev`。無料の脆弱性のデータベース）と `pypi.org`。送るのは、ライブラリの名前と版だけ。
2. **Mac の `launchd` で、週に 1 回、自動で動かします**（`scripts/schedule_audit.sh install`）。→ 2026-11-16 に、毎日に変えた（下の「追記」）。
   - 既定は、毎週月曜の 9 時。`AUDIT_WEEKDAY` と `AUDIT_HOUR` で変えられる。
   - Mac が眠っていた時刻の分は、次に起きたときに動く（`launchd` の決まり）。
   - 見つかったときと、調べられなかったときだけ、Mac の通知を出す。通知の文は決めた文だけで、ライブラリの出力をそのまま出さない。
   - 登録はオーナーが行う（Mac に残る変更なので）。`status` で状態と最後の結果、`run` ですぐ 1 回、`remove` で解除。
3. **ライブラリを変えたとき（`uv.lock` や `sandbox/requirements.txt` を変えたとき）は、その場でも `bash scripts/audit_deps.sh` を実行します**（AGENTS.md の作業の決まり）。

## 検討した案

| 案 | 内容 | 料金 | 良い点 | 困る点 |
|---|---|---|---|---|
| **A. Mac の launchd で週に 1 回（提案）** | 手元の Mac で、スクリプトを自動で動かす | 0 円 | 追加の契約がない。いまの構成のまま使える。結果が手元に残る | Mac を長く使わないと動かない。AWS に移ったら、別の仕組みが要る |
| B. 気づいたときに手で動かす | `bash scripts/audit_deps.sh` を、イメージを作り直す前などに実行する | 0 円 | 仕組みが要らない | 忘れる。ライブラリを変えていない期間に見つかったものに気づけない |
| C. GitHub の Dependabot | リポジトリに置き、GitHub に見てもらう | 0 円（GitHub の無料の範囲） | 直すための変更まで作ってくれる | いまは Git のリポジトリではない。コードを GitHub に置く判断が要る |
| D. AWS で定期実行（EventBridge と CodeBuild など） | AWS の中で、週に 1 回動かす | 少額（ビルドの時間の分） | 最終的な実行環境（ADR-0009）と同じ場所で動く | いまは AWS の環境がない |
| E. アプリの定時実行（ADR-0006）で動かす | エージェントの定時実行に任せる | モデルの料金 | 仕組みを足さない | アプリのコンテナには `uv` もロックファイルもない。エージェントに外へつなぐ操作をさせることになる |

いまは A を提案します。AWS で動かすときに D へ移ります（ADR-0009 の構成を決めるとき）。

## 確かめたこと（2026-11-15）

- いまのライブラリ: アプリの 174 個も、コードを実行する環境の 28 個も、既知の脆弱性は 0 件。
- 見つかったとき: 古い版のライブラリ（`requests 2.19.0`）だけを入れた仮のフォルダで試した。アプリ・コードを実行する環境とも「見つかった（脆弱性 38 件）」と出て、終了コードは 1。
- 調べられないとき（ネットワークなし）: 「調べられなかった」と出て、終了コードは 2。理由（OSV に届かなかった）は、結果のファイルに残る。
- 判定は、`uv audit` の結果の 1 行目（`Found N known vulnerabilities ...`）で行う。エラーの文に「vulnerability」が入っていても、「見つかった」とは誤らない。
- 自動実行の登録（`install`、`status`、`run`、`remove`）は、`launchctl` の代わりに `echo` を使って試した。作られる設定のファイルが正しいことを `plutil -lint` で確かめた。本物の登録は、オーナーが行う。
- 作っている途中で、2 つの問題を見つけて直した。
  - macOS の `mktemp` は、場所を書かないと `$TMPDIR` を見ない。
  - 全角の記号が変数名の直後にあると、bash が変数名の一部と読む（`"$PLIST）"`）。

## 分かっている制約

- **調べるのは、Python のライブラリだけです。** コンテナのイメージの土台（`python:3.12-slim` の Debian のパッケージ）や、Chainlit の画面の JavaScript は調べません。調べるなら、Trivy（無料。自前で動かせる）でイメージを調べる形を、別に考えます。
- **見つかったあとに直すのは、人です。** 版を上げて `uv lock`（アプリ）か `uv pip compile`（コードを実行する環境）をやり直し、テストを通して、イメージを作り直します。
- **Mac を使っていない期間は、動きません。** 次に起きたときに、1 回だけ動きます。
- **`uv audit` は、`uv` の試験中の機能です**（`--preview-features audit` で注意書きを消している）。`uv` を上げたときに、出力の形が変わることがあります。そのときは、判定の行を直します。

## 見直す条件

- AWS で動かす構成を決めるとき（案 D に移る）。
- コードを GitHub に置くことにしたとき（案 C を足す）。
- `uv audit` の出力の形が変わったとき。

## 追記（2026-11-16）: 週に 1 回から、毎日に変えた

- **オーナーの決定:** 「依存ライブラリのチェックは毎日しないとですね」。脆弱性は、見つかった日に知るほうがよい。
- **変えたこと:** `scripts/schedule_audit.sh install` の既定を、毎日 9 時にした（launchd の設定で、曜日を書かない）。
  - 時刻は、これまでどおり `AUDIT_HOUR` で変えられる。
  - `AUDIT_WEEKDAY` を書いたときだけ、その曜日の週に 1 回になる（これまでの形）。
- **料金:** 変わらない（0 円）。調べる先（OSV と pypi.org）への問い合わせが、週に 1 回から毎日になるだけ。
- **確かめたこと:** `launchctl` の代わりに `echo` を使って試した。
  - 毎日の登録では、作られる設定に曜日が入らない（`{'Hour': 9, 'Minute': 0}`。`plutil -lint` で OK）。
  - `AUDIT_WEEKDAY=1 AUDIT_HOUR=7` では、月曜 7 時になる。
  - `AUDIT_WEEKDAY=7` は断る。
- **結果のファイル:** `logs/audit/` に、1 日 1 つずつ増える（1 つは数 KB）。消す仕組みはない。
