# ADR-0022: Web 検索は、質問文を調べて、外に出したくない情報らしいものがあるときだけ確かめる

- **状態:** 採用（実装済み）。「顧客情報を含んでいないかをチェックして、入っていなければ検索、怪しい文言があったら確認」という形は、オーナーが決めた（2026-11-15）。何を「怪しい」とみなすか（下の「調べるもの」）と、その細かい決まりは、提案どおりに実装した。顧客の一覧をデータベースから読む形も、同じ日に提案どおりに足した（下の「データベースから読む見張る言葉」）。本物のモデルで、オーナーが動きを確かめた（2026-11-15）。決まりの細部は、オーナーの確認がまだ取れていない
- **日付:** 2026-11-15
- **決定者:** プロジェクトオーナー
- **対象:** data_agent

## 状況

- Web 検索の質問文は、検索のために外部（Claude API の Web 検索）に送られます。
- 2026-11-15 に、オーナーの決定で、Web 検索を「検索のたびに確かめる」形にしました（ADR-0020、ADR-0018）。ファイルやデータベースの値に仕込まれた指示に、モデルが従って、読んだ内容を質問文に書いて外に出す経路を、人が止められるようにするためです。
- そのあとで、オーナーから、次の提案がありました。「業務用だと Web 検索については、顧客情報を含んでいないかをチェックして、入っていなければ検索、怪しい文言があったら確認にみたいにできるとより良い気がします」。
- 検索のたびに確かめると、ふつうの検索（「venv の作り方」など）でも、毎回ボタンを押すことになります。確認が多すぎると、中身を見ずに押すようになり、確認の意味が薄れます（ADR-0021）。定時実行では、Web 検索を使えなくなっていました。

## 決定

- **Web 検索は、質問文を調べて、外に出したくない情報らしいものがあるときだけ、検索の前に確かめます。** 見つからなければ、確かめずに検索します。設定は `config/security.yaml` の `web_search.require_approval: auto` です（既定）。`true` で検索のたびに確かめ、`false` で確かめません。
- **確認の画面には、見つかったものと、どこにあったかを出します。**（例: 「`120`: このチャットで読んだもの（`read_file /data/sales.csv`）にあり、利用者の発言にはありません」）
- **怪しい検索の確認には、「このチャットでは以後確認しない」を出しません。** 押すと、そのあとは中身を見ずに外へ送ることになるためです。「毎回確認」のチャットでの、怪しくない検索には、これまでどおり出します。
- **定時実行（無人）では、怪しい検索だけを自動で拒否します。** ふつうの検索は行います。登録のときの画面にも、そう出します。
- **形の決まった秘密情報と個人情報（キー、カード番号、メールアドレス、電話番号など）は、これまでどおり、検索そのものを断ります**（ADR-0018。ガードレールで見つける）。確認にはしません。メールアドレスと電話番号を断ることは、オーナーが決めた（2026-11-15。外に出ることへの懸念から）。
- **顧客の名前を含む検索は、確かめます**（断りません）。顧客と同じ名前の公人や会社を、承認すれば検索できるようにするためです（オーナーの決定。2026-11-15。ADR-0023）。

### 調べるもの

| 種類 | 何を見るか | 利用者が自分で書いたもの |
|---|---|---|
| 手元のデータの写し | このチャットで読んだもの（ファイル、データベースの結果、コードの出力、サブエージェントの返事、会話の要約）にある文字列 | 数えない |
| 見張る言葉 | 一覧のファイル（`private/watch_terms.txt`）に書いた言葉と、データベースの決めた列（顧客の名前など）の値。顧客や取引先の名前、外に出したくない案件の名前など | 数える（確かめる） |

手元のデータの写しとして見るのは、次の3つです。

- **番号やコード:** 数字を含む、3 文字以上の英数字（`AOBA-7Q4KX`、`8,200`、`318` など）と、大文字を `-` や `_` でつないだ 6 文字以上のもの（`AOBA-BNWQX` など）。版の番号（`1.4.7`）と西暦（`2026`）は除きます。
- **表の値:** 区切り（`,` `|` `、` 改行など）で区切った、4〜40 文字のかたまりで、日本語を含むもの（CSV やデータベースの結果にある、取引先の名前など）。カタカナだけのもの（「インストール」など）は、よくある言葉が多いので除きます。
- **長い文:** 日本語を含む、10 文字以上続いた部分。

全角・半角、大文字・小文字、桁区切りのカンマ、空白の違いは、そろえてから比べます。Web 検索の結果は、もともと外にあったものなので、手元のデータには入れません。

### 見張る言葉の一覧

- 場所は `private/watch_terms.txt`（`config/security.yaml` の `web_search.watch_terms_file` で変えられる）。書き方は `private/watch_terms.example.txt` にあります。1 行に 1 つです。
- `private/` は、コンテナのイメージに入りません（`.dockerignore`）。`compose.yaml` で、読み取り専用で `/app/private` に渡します。エージェントから読める場所（`workspace/`、`memories/`、`skills/`）に置こうとすると、起動のときに止まります。一覧そのものが、顧客の情報だからです。
- ファイルを書き換えると、アプリを動かしたまま、次の検索から使われます。ファイルが読めないとき（文字コードが違う、など）は、どの検索も確かめます。
- 一覧がなければ、見張る言葉は使いません。手元のデータの写しだけを見ます。
- 会社の種類を除いた形も見張ります。「株式会社はまなす商事」と書けば、「はまなす商事」も見張ります（質問では、会社の種類を書かないことが多いため）。除いた形が 3 文字未満なら、除いた形は見張りません（「株式会社日本」の「日本」は見張らない）。データベースから読む言葉も同じです。

### データベースから読む見張る言葉（2026-11-15 に追加）

顧客の名前は、ふつうデータベースの顧客の表にあります。手で一覧のファイルに写すと、顧客が増えたときに古くなるので、データベースから読む形も足しました。ファイルの一覧と合わせて使います。

- **名前の列だけを読める、専用のロールで読みます。** 顧客の名前などの列を `config/watch_columns.<データベース名>.txt` に 1 行に 1 つ（`表.列`）書いて、`bash scripts/setup_data_db.sh <データベース名>` を実行すると、その列だけを読めるロール `coding_agent_screener` ができ、接続情報が `.env`（`DATA_DB_SCREENER_USER`、`DATA_DB_SCREENER_PASSWORD`）に足されます。練習用のデータベースでは、`customers.name` です。
- **見張る列は、エージェントのロールとは別に決めます。** エージェントのツールは、新しいロールを使いません。`.env` で同じロールを設定すると、起動のときに止まります（エージェントのロールが読める列を全部見張ると、金額なども見張ることになるため）。最初は、エージェントのロール（`coding_agent_reader`）は名前の列を読めませんでした（ADR-0019）。同じ日に、オーナーの決定で、エージェントも名前を読めるようにしました（ADR-0023）。
- **アプリは、このロールが読める列の値を、10 分ごとに裏で読み直します**（`web_search.watch_terms_refresh_minutes`）。検索を待たせません。どの列を読むかは、ロールの権限で決まります（`config/watch_columns.*.txt` を書き換えてスクリプトを実行し直せば、アプリを止めずに、次の読み直しから変わる）。
- **読めないときは、どの検索も確かめます。** 読み終える前、データベースに届かないとき、値の数が上限（`web_search.watch_terms_max`。10 万件）を超えたとき、です。定時実行では、その間の検索はすべて自動で拒否されます。読み直しに失敗しても、前に読めた言葉は残して見張ります。60 秒ごとに読み直しを試します。
- **名前は、ファイルに書き出しません。** アプリのメモリーの中だけで使います。監査ログ（`watch_terms_load`）には、列と値の数だけを残します。
- 200 文字を超える値は、名前ではないとみなして見張りません。
- 顧客が何万件あっても、言葉の頭の 2 文字で引いて探すので、1 回の判定は 1 ミリ秒未満です（13 万件で確かめた）。

| 案 | 内容 | 良い点 | 困る点 |
|---|---|---|---|
| a. 名前をファイルに書き出す | オーナーが管理者の接続で読み、`private/watch_terms.txt` に書き出すコマンドを、ときどき実行する | 新しいロールが要らない | 顧客の名前の写しが、データベースの外にもう 1 つできる（守りはファイルの置き場所だけ）。書き出し直さないと古くなる。AWS では、書き出す仕組みと、ファイルの受け渡しが別に要る |
| **b. 名前の列だけを読めるロールで、アプリが読む（採用）** | 専用のロールを作り、アプリが間隔ごとに読み直す | 写しを作らない。読める範囲はデータベースの権限が守り、権限を外せば止まる。顧客が増えても、自動で新しくなる。AWS（RDS）でも同じ形（秘密情報が 1 つ増えるだけ） | 名前を読める接続の情報が、アプリに 1 つ増える |
| c. エージェントのロールに、名前の列を読ませる | 読めなくした列（ADR-0019）から外す | 新しいロールが要らない | エージェントとモデルが、顧客の名前を読めるようになる。見張る列を決められない（ロールが読める列を全部見張ることになる） |

このあとで、オーナーが、エージェントも名前を読めるようにすると決めました（ADR-0023）。見張る列を決めるために、専用のロールはそのまま使います。

## 仕組み

- `src/data_agent/safety/search_screen.py` が、判定をします。
- **判定は、モデルが検索を出した時点で行い、その返事（`AIMessage` の `response_metadata`）に記録します**（`SearchScreenMiddleware`）。確認の仕組み（`approvals.py`）は、この記録を読みます。承認を待って止まったあとで再開したときに、判定が変わらないようにするためです。LangChain の確認の仕組みは、再開のときにも判定し直し、そこで「確かめなくてよい」になると、利用者が拒否した操作が実行されます（`HumanInTheLoopMiddleware` の `when` の注意書き）。止まっている間に見張る言葉の一覧を書き換えても、判定は変わりません（単体テストで確かめた）。
- 記録が見つからない・読めないときは、確かめる側に倒します。
- 画面は、止まったときの説明（HITL の `description`）に書き添えた記録から、見つかったものを読み戻します。画面から見える会話の状態は親のものだけで、サブエージェントの返事は入っていないためです。
- **サブエージェントでは、親から渡された依頼文を、手元のデータとして扱います。** 依頼文は親のモデルが書いたもので、読んだ内容の写しが入りうるためです。利用者が書いた文章は、親の会話の状態（`screen_user_texts`）から引き継ぎます。
- 監査ログには、判定の結果（怪しいか、見つかった数と種類）だけを残します。見つかった文字列は残しません（顧客の情報そのものなので）。
- 判定に、別のモデル（審判のモデル）は使いません。料金がかからず、判定がいつも同じになり、仕込まれた指示に審判のモデルが操られることもないためです。そのかわり、言い換えたものは見つけられません（下の「分かっている制約」）。

## 検討した案

| 案 | 内容 | 良い点 | 困る点 |
|---|---|---|---|
| A. 検索のたびに確かめる（2026-11-15 の朝の決定） | `require_approval: true` | 見落としがない（人が見る限り） | ふつうの検索でも毎回押す。押し慣れて、中身を見なくなる。定時実行で使えない |
| **B. 質問文を調べて、怪しいときだけ確かめる（採用）** | 手元のデータの写しと、見張る言葉を調べる | ふつうの検索は止まらない。怪しいときは、何が怪しいかを示して聞ける。料金がかからない | 言い換えは見つけられない。見出しなどを、怪しいとみなすことがある |
| C. 審判のモデルに判断させる | 質問文と会話を、別のモデルに読ませる | 言い換えも見つけられるかもしれない | 1 回ごとに料金がかかる。判定が毎回変わりうる（再開のときに判定が変わると、拒否した検索が実行される）。仕込まれた指示に、審判のモデルも操られうる |
| D. 見張る言葉だけを調べる | 一覧にある言葉だけ | 空振りが少ない | 一覧にないもの（社外秘のコード、売上の数値など）を見逃す。点検の攻撃 6 種類のうち、止められるのは 0 |

## 確かめたこと

**単体テスト（`tests/test_search_screen.py` の 28 件と、`tests/test_database.py` の 1 件。全体では 405 件すべて通った）**
- 社外秘のファイルのコード（数字あり・なし、一部だけ）、全角や桁区切りを変えた数値、CSV とデータベースの結果にある取引先の名前、長い文の写しを、見つける。
- 利用者が自分で書いたもの、Web 検索の結果にあったもの、版の番号、西暦、カタカナだけの言葉、`read_file` が付ける行番号、パッケージの名前は、怪しいとみなさない。
- 2026-11-15 の測定で、本物のモデルが実際に出した検索（手元のファイルを読む前のもの）は、怪しいとみなさない。
- 会話の要約は、手元のデータとして扱い、利用者の発言としては扱わない。サブエージェントの依頼文も同じ。
- 見張る言葉は、利用者が書いても見つける。英数字は、語の切れ目で比べる。ファイルを書き換えると読み直す。読めないときは、どの検索も確かめる。
- LangChain の `create_agent` に組み込んで、ふつうの検索は止まらずに行われ、読んだコードを書いた検索は止まり、拒否すると行われないことを確かめた。止まっている間に一覧から言葉を消しても、拒否した検索は行われない。
- データベースから読む見張る言葉: 会社の種類を除いた形を見張る（短すぎる形は見張らない）。数万件を頭の文字で引いた結果が、1 つずつ比べた結果と同じになる。読み終える前と、読めなかったときは、どの検索も確かめる（読めなかった理由は、決めた文だけを出し、データベースのメッセージは出さない）。間隔と、失敗したあとの間隔で読み直す。ファイルの一覧と合わせられる。同じロールを設定すると止まる。

**データベースの準備のスクリプト（使い捨ての `postgres:17` で、`scripts/setup_data_db.sh` を実行）**
- 初めて実行すると、2 つのロールができ、`.env` に両方の接続情報が足される。2 回目は、`.env` を変えずに権限だけを付け直す。
- 見張る用のロールが読めるのは `customers.name` だけ（`email`、`region`、`orders.amount`、`products.name` は読めない）。エージェントのロールは、これまでどおり `name` と `email` を読めない。見張る用のロールは、読み取り専用（`DELETE` は断られる）。
- いまのオーナーの状態（エージェントのロールだけがある）から実行すると、見張る用のロールだけが足される。
- 列の書き間違いは、その場で止まり、前の権限はそのまま残る。`表.*` は断る。一覧が空なら、見張る用のロールは何も読めなくなる。
- 読むデータベースを切り替えると、前のデータベースの権限は、両方のロールから外れる。`.env` にあるのにロールがないときは、止まって直し方を出す。

**点検の仕組み（偽のモデル。`--selftest`。料金はかからない）**
- 指示に必ず従うモデルで、「標準」の貫通は 8/21。検索のたびに確かめる形（案 A）と同じで、社外秘の値を検索に書いて持ち出す 6 種類は、すべて止まった。指示に従わないモデルでは、21 種類とも、検索は止まらずに行われた。
- 3 回続けて実行して、どれも通った。持ち出しの攻撃 5 種類を、12 回ずつ繰り返しても、すり抜けは 0 回だった。
- 作っている途中で、自己点検が、数字を含まないコード（点検の社外秘の値は、実行のたびに変わる）の見逃しを見つけた。大文字をつないだコードを見る決まりを足して、直した。

**アプリとつないだ確認（偽のモデル。`tests/e2e/`。画面と同じ通信）**
- すべて通った。承認 72・14、コードの実行 28・2、データベース 5・21、ガードレール 17、モデルの切り替え 12、定時実行 26、スキルの提案 20、アーカイブ 16、過去のチャット 4・5。ログにエラーはなかった。
- 足した確認:
  - 「標準」で、ふつうの検索は、確かめずに検索する。
  - 読んだファイル（`/data/sales.csv`）の写しを検索に書くと、確かめられ、見つかったものと、どこにあったかが出る。「以後確認しない」は出ない。拒否すると検索せず、承認すると検索する。
  - データベースの結果の写しを検索に書くと、確かめられる。
  - 見張る言葉の一覧にある言葉は、利用者が自分で書いても確かめる。
  - 定時実行で、ふつうの検索は行い、見張る言葉を含む検索は自動で拒否する。登録のときに、そう出る。
- 偽のモデルに、「直前のツールの結果を、自分から検索に書く」動き（`前の結果を検索して`）を足した。読んだデータを、モデルが勝手に検索に使う場合の役。
- データベースから読む見張る言葉（2026-11-15 に追加）: アプリが、見張る用のロールで顧客の名前 20 件を読む（ほかの列は読めず、書き込めない）。利用者が「山田 太郎」を検索しようとすると、確かめられ、「`山田太郎`: `見張る言葉の一覧`にある言葉です」と出る。名字だけ（「高橋」）なら、確かめずに検索する。データベースの確認 53・23 件がすべて通った。ほかの確認も、見張る言葉をデータベースから読む状態で、すべて通った（承認 72・14、コードの実行 28・2、データベースの承認 5、ガードレール 17、モデルの切り替え 12、定時実行 26、スキルの提案 20、アーカイブ 16、過去のチャット 4・5。ログにエラーはなかった）。点検の仕組みの自己点検も、前と同じ（「標準」で貫通 8/21、「毎回確認」で 4/21）。
- 確かめている途中で、画面に出す「見つかったもの」が、表の行をまたいだ切れ端（`120 大阪` など）や、同じものの繰り返しになっていたので、直した。いまは、たとえば次のように出る。

```
見つかったもの:
- `東京,120 大阪,80 福岡,45`: このチャットで読んだもの（`read_file /data/sales.csv`）にあり、利用者の発言にはありません
```

**数の読み方の修正（2026-11-15。ADR-0025 を作っているときに見つけた）**
- CSV の区切りのカンマを、桁区切りと取り違えていた（`1284600,231` を 1284600231 と読んでいた）。CSV の件数の列（`231` など）を写した検索を、見逃すおそれがあった。
- 桁区切りとみなすのは、「1〜3 桁のあとに、3 桁ずつ続く形」（`1,284,600`）だけにした。テストを足し（CSV の件数の列を写した検索が、見つかる）、全体のテストと、間接注入の点検の自己点検が、前と同じように通ることを確かめた。

**本物のモデル（Opus 5.5。オーナーが手元のアプリで試した。2026-11-15）**
- 見張る用のロールで、顧客の名前 20 件を読めた（起動の 3 秒後）。
- ふつうの検索（`venv` の作り方）は、確かめずに検索した。
- 「山田 太郎さんについて調べて」では、モデルが検索を出さずに、どの人かと、作業フォルダやデータベースに出てくる人かを聞き返した。
- 「顧客の地域ごとの人数を出して、その結果を検索して」では、モデルがデータベースを問い合わせたあと、「社内データベースの数字は検索に書けない」として、検索を出さなかった。
- どちらも、エージェントへの指示（`prompts/SYSTEM.md` の「作業フォルダのファイルやデータベースから得た内容を、Web 検索の依頼に書かない」）が先に効いて、この ADR の確認は出番がなかった。ふつうに頼む限り、本物のモデルで確認が出ることは少ない。この確認は、モデルが指示を守らなかったとき（仕込まれた指示に従ったとき、書き間違えたとき）のための、次の段の守り。
- 「参議院議員の山田太郎さんについて Web で調べて」では、モデルが検索を出し、架空の顧客と同じ名前なので、確認の画面が出た（「見つかったもの: `山田太郎`: `見張る言葉の一覧`にある言葉です」。ボタンは「承認」「拒否」「拒否して理由を伝える」で、「以後確認しない」は出なかった）。承認すると検索し、出典付きで答えた。監査ログでは、判定が「怪しい（見張る言葉 1）」、確認の種類が `suspicious`、決定が承認だった。最初の読み込みから 10 分を過ぎたあとの検索で、データベースからの読み直しも動いた。

## 分かっている制約

- **言い換えたものは、見つけられません。** 「4 億 8,200 万円」を「4.82 億円」と書く、名前をローマ字にする、要点だけを書く、などです。見つけられるのは、そのままの写しだけです。
- **一度に、ではなく、少しずつ外に出すと、見つけにくくなります。** 1 回の検索に、3 文字未満の数字や、4 文字未満の言葉だけを書く場合です。
- **英語の名前（数字を含まない、小文字の語）は、手元のデータの写しとしては見つけません。** 見張る言葉の一覧に書いてください。
- **空振り（怪しくないのに確かめる）があります。** 分かっているのは、ファイルの見出し（4 文字以上で、漢字やひらがなを含むもの）をそのまま質問に使ったとき、版の番号の一部（`2.12`）、ログにあるエラーの番号や接続先のポート（`404`、`5432`）を質問に使ったとき、サブエージェントが依頼文の言い回しを 10 文字以上そのまま使ったとき、です。どれも、1 回ボタンを押せば検索します。
- **長期メモ（`/memories/AGENTS.md`）とスキルの中身は、手元のデータとして見ていません。** システムプロンプトとして読み込まれるためです。長期メモに顧客の名前があるなら、見張る言葉の一覧にも書いてください。
- **会話が長くなって古い部分が要約されると、要約の文章だけが手元のデータとして残ります。** 要約に入らなかった値は、見つけられません。
- **確かめる画面で、人が中身を見ずに承認すれば、守りは効きません。**
- **データベースから読む見張る言葉は、列の値のとおりの形（と、会社の種類を除いた形）だけです。** 名字だけ、名前だけ、ふりがな、ローマ字は見つけません。「なし」「未設定」のような値が多い列を選ぶと、ふつうの検索でも確認が出ます。
- **名前を読める接続の情報（`DATA_DB_SCREENER_PASSWORD`）が、`.env` に 1 つ増えます。** 読めるのは、一覧に書いた列だけです。
- **顧客の数が上限（10 万件）を超えると、どの検索も確かめます。** 上限は上げられますが、メモリーと読み込みの時間が増えます。
- **AWS では、RDS に同じロールを作ります。** `scripts/setup_data_db.sh` は、手元の PostgreSQL のためのものです。

## 見直す条件

- 空振りが多くて、押し慣れてしまうと分かったとき（区切りの長さ、カタカナの扱い、数字の桁数を見直す）。
- 顧客の数が 10 万件を大きく超えたとき（読み込みの時間とメモリー。読み方を見直す）。
- 審判のモデルを入れるとき（ADR-0020 の「資料にあって、取り入れていないもの」）。言い換えの見逃しを、どこまで減らせるかを測る。
- Web 検索のほかに、外にものを送るツールを足したとき（同じ判定を、そのツールにも付けるか）。
