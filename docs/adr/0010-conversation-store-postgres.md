# ADR-0010: 会話は PostgreSQL に保存し、Langfuse と同じクラスタに別のデータベースとして置く

- **状態:** 採用
- **日付:** 2026-11-13
- **決定者:** プロジェクトオーナー
- **対象:** data_agent

## 状況

- 会話はメモリ上にしか保存されておらず、アプリを止めると消えていました（ADR-0003）。
- 最終的な実行環境の ECS では、コンテナが入れ替わるたびにメモリが消えます。会話を外に保存する必要があります（ADR-0009）。
- オーナーの方針は次の2点です。
  - 会話の履歴は、pgvector が使える PostgreSQL に保存する。
  - Langfuse が使っている PostgreSQL と同じクラスタで動かす。
- 手元では Langfuse が Docker で動いていて、その PostgreSQL は 17.9（`postgres:17` イメージ）です。brew_app と studyops も、この Langfuse を使っています。

## 決定

- **会話は PostgreSQL に保存します。** LangGraph のチェックポインタを `AsyncPostgresSaver` にします。
- **Langfuse と同じクラスタに、別のデータベース `coding_agent` を作って使います。** Langfuse のデータベース（`postgres`）は共有しません。
- **アプリ専用のロール `coding_agent` を使います。** 管理者権限は持たせず、`coding_agent` データベースの持ち主にするだけです。ほかのロールは、このデータベースに接続できません。
- **`DB_HOST` を設定したときだけ PostgreSQL に保存します。** 設定しなければ、これまでどおりメモリ上に保存します。
- **PostgreSQL につながらないときは、起動を止めます。** メモリ上の保存には切り替えません。保存されているつもりで消えていた、という事態を防ぐためです。
- **pgvector は、意味検索を足すときに有効にします。** 会話の履歴そのものは通常のテーブルに入るので、pgvector がなくても保存できます。

## 仕組み

| 項目 | 内容 |
|---|---|
| **接続情報** | `.env` の `DB_HOST`、`DB_PORT`、`DB_NAME`、`DB_USER`、`DB_PASSWORD`、`DB_SSLMODE` |
| **テーブル** | `checkpoints`、`checkpoint_blobs`、`checkpoint_writes`、`checkpoint_migrations`。アプリが起動時に作る |
| **手元での準備** | `scripts/setup_local_db.sh` がデータベースとロールを作り、接続情報を `.env` に追記する |
| **コンテナからの接続** | `compose.yaml` で Langfuse のネットワーク（`langfuse_default`）に参加し、`postgres:5432` に接続する |
| **AWS での接続** | Langfuse と同じ RDS のクラスタに、データベースとロールを同じ形で作る。パスワードは Secrets Manager に置き、`DB_SSLMODE=require` にする |

## 検討した選択肢

| | A. Langfuse と同じクラスタの別データベース（採用） | B. Langfuse と同じデータベースを共有 | C. 専用の PostgreSQL を別に立てる |
|---|---|---|---|
| **運用するもの** | クラスタは1つ | クラスタは1つ | クラスタが2つ |
| **Langfuse との分離** | データベースとロールで分かれる | テーブルが混ざる。Langfuse の更新とぶつかる恐れがある | 完全に分かれる |
| **費用** | 追加なし | 追加なし | 1台分増える |
| **障害の影響** | クラスタが止まると両方止まる | 同じ | 互いに影響しない |

## 確かめたこと（2026-11-13）

手元の Langfuse の PostgreSQL には手を加えず、同じ版（`postgres:17`）の使い捨てのコンテナで確かめました。

**確認できたこと**
- セットアップ用スクリプトが、データベースとロールを作り、接続情報を追記する。2回目の実行では何も変更しない。
- アプリが PostgreSQL に接続し、保存用のテーブルを自分で作る。
- 書き込んだ会話を、アプリのコンテナを再起動したあとに、別のプロセスから読み出せる。
- パスワードが違うと、約17秒でエラーを出して終了する（終了コード 3）。
- `coding_agent` ロールは、管理ユーザーが持つテーブル（Langfuse のテーブルに相当）を読めない。
- ほかのロールは、`coding_agent` データベースに接続できない。
- 単体テスト 14 件が通る。

**確認していないこと**
- 画面からモデルとやりとりした会話が保存されること。API キーを使っていないためで、確認ではエージェントの状態に会話を直接書き込みました。
- 手元の Langfuse の PostgreSQL での動作。セットアップ用スクリプトは `.env` に追記するので、オーナーが実行します。
- AWS の RDS での動作。

## 分かっている制約

- **保存した会話を、画面から呼び出せません。** 今の画面には過去のチャットを開き直す機能がなく、チャットを開くたびに新しい会話になります。会話はデータベースに残りますが、利用者からは見えません。呼び出せるようにするには、Chainlit の履歴保存（データ層）を足す必要があります。
- **手元の Langfuse の PostgreSQL には pgvector が入っていません。** 入れるには、Langfuse の compose のイメージを pgvector 入りのものに替える必要があります。Langfuse と、それを使う brew_app・studyops に影響するので、替えるかどうかはオーナーの判断待ちです。AWS の RDS では、拡張機能として有効にできる見込みです（要確認）。
- **コンテナが Langfuse のネットワークに参加します。** PostgreSQL 以外の Langfuse のサービス（Redis、ClickHouse など）にも、ネットワークの上では届くようになります。AWS では、セキュリティグループで PostgreSQL だけに絞ります。
- **`coding_agent` ロールは、Langfuse のデータベースに接続すること自体はできます。** PostgreSQL の既定の設定によるものです。テーブルの中身は読めません。接続も禁じるには Langfuse 側のデータベースの権限を変える必要があるので、行っていません。
- **クラスタを共有するので、接続数の上限も共有します。** 上限は 100 で、アプリが開く接続は最大 5 です（`DB_POOL_MAX`）。

## 追記（2026-11-13）

「保存した会話を、画面から呼び出せません」という制約は解消しました。左側の一覧から過去のチャットを開き直せるようになっています（ADR-0011）。

## 実装の途中で分かったこと

- **Chainlit は、起動時の処理で起きたエラーを記録するだけで、起動を続けます。** そのままだと、データベースにつながらなくても画面だけが動きます。起動時にエラーが起きたらプロセスを終了するようにしました（`ui/app.py` の `_startup`）。
