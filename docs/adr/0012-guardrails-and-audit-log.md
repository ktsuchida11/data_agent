# ADR-0012: ガードレールは「形が決まっている情報をルールで守る」ことから始め、監査ログを足す

- **状態:** 一部置き換え済み（→ ADR-0019: メールアドレスと電話番号を、既定でマスクするように変えた。検出ルールも、日本語に続けて書かれたものと表記ゆれを見逃さない形に直した）。そのほかは採用。オーナーは提案に変更を加えず、続行を指示した。種類ごとの扱いは提案どおりの既定値で実装し、設定で変えられる。Langfuse へのトレースの送信は ADR-0015 に分けた
- **日付:** 2026-11-13
- **決定者:** プロジェクトオーナー
- **対象:** data_agent

## 状況

- README のフェーズ3に「入口・出口のガードレール（ルール＋Presidio＋LLM Guard）と監査ログ」とありますが、具体的な設計はしていませんでした。
- 会話とツールの入出力を PostgreSQL に保存するようになりました（ADR-0010、ADR-0011）。利用者が貼り付けた秘密情報が、そのままデータベースに残る状況になっています。
- 最終的には AWS で複数人が使う想定です（ADR-0009）。誰が何をしたかを、あとから追える必要があります。

### 今ある守りと、足りないところ

| 心配ごと | 今ある守り | 足りないところ |
|---|---|---|
| **秘密情報がモデルや保存先に流れる**（API キー、パスワード、秘密鍵） | `.env` や鍵ファイルは、名前で読み書きを禁止している。指示文で「書かない・答えに含めない」と指示している | 利用者が貼り付けた場合と、ふつうのファイルの中に書かれている場合は素通りする |
| **個人情報が流れる** | 指示文での指示だけ | 同上 |
| **ファイルなどに紛れた指示に従ってしまう**（プロンプトインジェクション） | 作業フォルダの外に出られない。削除とメモリへの書き込みは承認制。スキルは書き換えられない。コード実行と外部への通信はまだない | 検出の仕組みはない |
| **暴走する** | モデルとツールの呼び出し回数に上限がある | — |
| **あとから追えない** | なし | 監査ログがない |

### 候補の部品について分かったこと

| 部品 | 分かったこと |
|---|---|
| **LangChain の `PIIMiddleware`** | すでに入っている。メール、カード番号、IP アドレスなどを検出でき、正規表現や関数で独自の検出ルールを足せる。入力、出力、ツールの結果のそれぞれに適用でき、扱いは「止める」「置き換える」「一部を隠す」「ハッシュにする」から選べる |
| **LLM Guard** | 検索結果によると、2026年7月にアーカイブされ、開発が終わっている。最後の版は 2025年5月の 0.3.16。確度の低い情報源も含むので、採用を検討する場合は GitHub で確認が必要 |
| **Presidio** | 日本向けの検出器（マイナンバーなど）は、標準では見つからなかった。検出器は言語ごとに用意する作りで、日本語は自作が必要。氏名や住所の検出には、別に日本語の言語モデルが要る |

## 決定（提案）

### 1. 検出は、まずルールだけで行う

- **LangChain 標準の `PIIMiddleware` に、独自の検出ルールを足して使います。** 新しい依存は増やしません。（実装では、同じ差し込み口を使う自前のミドルウェアに変えました。下の「実装」を参照）
- **LLM Guard は使いません。** 開発が終わっているためです。
- **Presidio は、今は入れません。** 氏名や住所のように形が決まっていない個人情報の検出が必要になったら、そのときに足します。

### 2. 守る場所は3か所

| 場所 | 対象 | 扱い |
|---|---|---|
| **入口**（利用者の入力） | 秘密情報、個人情報 | マスクしてからモデルに渡す。画面とデータベースに残る入力も、マスクしたものに差し替える。マスクしたことを利用者に知らせる |
| **ツールの結果**（読んだファイルの中身など） | 秘密情報、個人情報 | マスクしてからモデルに渡す |
| **出口**（モデルの返事、ファイルへの書き込み） | 秘密情報 | 返事はマスクする。ファイルへの書き込みは拒否し、理由をモデルに返す |

### 3. 種類ごとの扱い

| 種類 | 例 | 扱い（提案） |
|---|---|---|
| **秘密情報** | Anthropic・OpenAI・AWS・GitHub・Google・Slack の API キーの形式、秘密鍵のブロック | マスクする |
| **個人情報（危険が大きく、形が決まっているもの）** | クレジットカード番号、マイナンバー | マスクする |
| **個人情報（開発でふつうに出てくるもの）** | メールアドレス、電話番号 | 記録するだけ。テスト用のデータなどで出てくるので、マスクすると作業を壊すため |

種類ごとの扱い（マスク・記録だけ・何もしない）は、`config/security.yaml` で変えられるようにします。

### 4. プロンプトインジェクションは、検出ではなく「できることを絞る」で守る

- 検出モデルは入れません。日本語での精度が分からず、すり抜けを前提にする必要があるためです。
- 今の守り（作業フォルダの外に出られない、危険な操作は承認制、スキルは書き換えられない）を続けます。
- コード実行や外部への通信を足すとき（フェーズ2、フェーズ4）は、それぞれに許可リストと承認を付けます。

### 5. 監査ログを足す

- **出し先は標準出力です。** 1件を1行の JSON で出します。ECS では CloudWatch に集まり、保存期間と閲覧の権限をそこで管理できます。
- **内容そのものは記録しません。** 会話の中身はデータベースの履歴にあるので、監査ログには「誰が・いつ・何をしたか」だけを残します。

| 記録するできごと | 記録する項目 |
|---|---|
| ログインの成功と失敗 | 利用者名、時刻 |
| チャットの開始、再開、削除、アーカイブ | 利用者、チャットの ID |
| 依頼の受け付け | 利用者、チャットの ID、文字数 |
| ツールの呼び出し | ツール名、対象のパス、成功か失敗か |
| 承認の判断 | 対象の操作、承認か拒否か |
| ガードレールの検出 | 場所（入口・ツールの結果・出口）、種類、件数。検出した値は記録しない |
| 上限への到達 | どの上限か |

## 実装（2026-11-13）

提案から1点だけ変えました。

- **`PIIMiddleware` は使わず、同じ差し込み口を使う自前のミドルウェアにしました**（`guard_middleware.py`）。理由は3つです。
  - `PIIMiddleware` には「記録するだけ」の扱いがありません。
  - `PIIMiddleware` は種類ごとに1つずつ必要で、そのたびにエージェントの処理の段が増えます。自前のものは1つで済みます。
  - 書き込みの拒否と監査ログを、同じ場所で扱えます。

| ファイル | 役割 |
|---|---|
| `src/data_agent/safety/guardrails.py` | 検出ルールとマスク |
| `src/data_agent/safety/guard_middleware.py` | エージェントへの差し込み（モデルに渡す直前、ツールの結果、モデルの返事、書き込みの拒否） |
| `src/data_agent/safety/audit.py` | 監査ログ |
| `config/security.yaml` の `guardrails` | 種類ごとの扱い |

- **サブエージェントにも付けています。** サブエージェントは親のミドルウェアを引き継がないためです。Deep Agents が標準で足す汎用のサブエージェントは、同じ名前で定義し直して、ガードレールを付けました。
- **入口では、保存先も書き換えます。** Chainlit は、利用者のメッセージ、チャットの名前、処理の記録（`on_message` の行）の3か所に入力の文章を保存します。3か所とも、マスクしたものに置き換えます。（→ 2026-11-18: 保存の手前でもマスクするようにした。置き換えは保存を 1 秒待ってから行うので、保存が遅いと、マスクする前の文章が残ることがあった。ADR-0034）
- **マスク済みの値の書き戻しも拒否します。** モデルは、マスクされたファイルの中身を見ています。それをそのまま書き戻すと、ファイルにあった元の値が失われるためです。

### 確かめたこと

使い捨ての PostgreSQL と偽のモデルを使い、画面と同じ通信で確かめました。キーや番号は、形だけを合わせた偽物です。

**確認できたこと**
- 利用者が貼り付けたキーは、マスクされてからモデルに渡る。マスクしたことが利用者に知らされる。
- 貼り付けたキーは、画面の履歴にも、チャットの名前にも、エージェント側の保存にも残らない（データベースの全部の表を検索して確認）。
- ファイルの中のキーは、モデルに渡る前にマスクされる。サブエージェント（調査役、汎用役）が読んだ場合も同じ。
- キーを含む書き込みと、マスク済みの値を含む書き込みは拒否され、ファイルは作られない。元のファイルは変わらない。
- カード番号はマスクされる。メールアドレスは、既定ではマスクされず、記録だけされる。
- 監査ログに、ログイン、チャットの開始と再開、依頼、ツールの呼び出し、書き込みの拒否、ガードレールの検出、チャットの削除・アーカイブ・グループ分けが出る。
- 監査ログとコンテナのログのどこにも、キー、カード番号、メールアドレスの値は出ない。
- 前回までの確認（一覧・再開・削除、アーカイブ・グループ分け）が、引き続き通る。
- 単体テスト 45 件が通る。

**確認していないこと**
- 本物のモデルでの動き。モデルの返事に秘密情報が含まれた場合のマスクは、単体テストでだけ確かめています。
- ブラウザの画面での見え方。
- 承認を求める画面に出る引数のマスク。

### 残っている点

- **モデルが自分から書こうとした文字列は、エージェント側の保存に残ります。** 書き込みは拒否され、画面の履歴にも残りませんが、モデルの発言の一部として会話の保存（チェックポイント）には入ります。モデルが見る内容はマスク済みなので、本物の秘密情報がここに入ることは考えにくいです。
- **返事は、流れている途中はマスクされません。** 文字が流れ終わって確定するときにマスクします。
- **ブラウザの側に残る入力の履歴は、書き換えられません。** Chainlit の画面には「最近の入力」を出す機能があり、ブラウザが元の文章を覚えている可能性があります（未確認）。
- **上限に達したことは、まだ監査ログに出ません。**（2026-11-14 に、回数の上限の作り直しとあわせて、出るようにした。ADR-0020）
- **数字の誤検出があります。** 12桁の数字は、約11個に1個がマイナンバーの検査用数字に合い、マスクされます。困る場合は、`my_number` を `log` か `off` にします。

## 検討した選択肢

| | A. ルールだけ（採用） | B. ルール＋Presidio | C. ルール＋Presidio＋LLM Guard（README の当初案） |
|---|---|---|---|
| **検出できるもの** | 形が決まっているもの（キー、カード番号、マイナンバーなど） | A に加えて、氏名や住所（日本語の検出器と言語モデルを用意すれば） | B に加えて、インジェクションらしい文章 |
| **追加で要るもの** | なし | Presidio、日本語の言語モデル、自作の検出器 | B に加えて LLM Guard と検出モデル |
| **イメージの大きさと速度** | 変わらない | 大きく、遅くなる | さらに大きく、遅くなる |
| **保守** | 自分のルールだけ | 検出器の調整が要る | LLM Guard は開発が終わっている |

## この方式の限界

- **形が決まっていない秘密情報は見つけられません。** 独自の形式のパスワードや、ルールにないサービスのキーは素通りします。
- **氏名や住所は見つけられません。**
- **マスクすると、作業に必要な値まで隠れることがあります。** たとえば、設定ファイルのキーを書き換える作業はできなくなります。その場合は、利用者が自分でファイルを編集します。

## 影響

- 利用者が貼り付けた API キーが、モデルにもデータベースにも残らなくなります。
- 監査ログを、スキルの自動化（ADR-0007）の材料にもできます。ただし、操作の中身はデータベースの履歴にあるので、そちらを使うほうが向いています。
- 起動時に読む設定（`config/security.yaml`）が増えます。
