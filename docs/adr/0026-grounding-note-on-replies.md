# ADR-0026: 返事の数と URL を根拠と照合し、確かめられないものに注記を出す（誤情報の守り。OWASP LLM09）

- **状態:** 採用（実装済み）。オーナーが決めた（2026-11-15。提案した 4 つの案のうち、おすすめの 1 と 2）。本物のモデルの返事（誤情報の点検の 36 件）で、注記の出方を確かめた（2026-11-15）。ふだんの使い方での確認は、まだ（オーナー）。2026-11-16 に、注記の取りこぼし（定時実行の返事と、ツールを呼ぶ前に話した文）を直した（下の「追記」）
- **日付:** 2026-11-15（追記 2026-11-16）
- **決定者:** プロジェクトオーナー
- **対象:** data_agent

## 状況

- 誤情報（作り話）は、ADR-0025 で測れるようにした。2026-11-15 の測定では、3 つのモデルとも作り話は 0/12 だった。
  - ただし、12 問は短く素直な質問です。長い表、あいまいな依頼、何段階もの作業では起こりえます。
  - 測るだけでは、ふだん使うときの作り話は防げません。
- 使うときの守りは、Web 検索の結果に出典が付くことと、計算をコードの実行でできることだけでした。プロンプトにも、数と出典の決まりはありませんでした。
- オーナーの発表資料（ガードレールと評価）の考え方は、次のとおりです。
  - 速く確かなものは、その場で規則で見る。重い判定は後から見つけて、人が確かめ、規則にする。
  - 回答の「品質ゲート」は、出典があるか・引用が実在するか・数値が根拠にあるかを、プログラムで判定していた。
  - ただし、形の検査では、数値の取り違えや増減の逆転のような中身の誤りは通ってしまう、という結論だった。

## 決定

4 つの案のうち、**1（プロンプトの決まり）と 2（返事の照合と注記）**を入れます（オーナーの決定）。

**1. プロンプトの決まり**（`prompts/SYSTEM.md` の「数と出典」）
- 数を答えるときは、どこから取ったか（ファイルと行や列、データベースの表、検索の出典）を添える。
- 合計・平均・差などの計算は、コードの実行かデータベースの集計で出す。できなかったときは、手で計算したことを書く。
- 答えが見つからないときは、見つからなかったと書く。それらしい数を作らない。
- 開いていない URL や、検索結果にない URL を、出典として書かない。

**2. 返事の照合と注記**（`grounding.py`、`ui/app.py`）
- **規則:** 誤情報の点検（ADR-0025）の判定と同じ規則を使う。規則は `grounding.py` に移し、点検の判定（`evals/factcheck/judge.py`）もそれを使う。測った規則と、使うときの規則がずれないようにするため。
  - データらしい数（3 桁以上の数と小数）と URL が、根拠にあるか。
  - 読んだ表から出せる簡単な計算（列の合計と平均、行のまとまりごとの合計と平均、2 つの値の和と差）は、合っていれば根拠ありとする。
  - 確かめ先として案内しただけの URL（「〜で確かめてください」）は、数えない。
- **根拠:** このチャットの、利用者の発言、ツールの結果（サブエージェントの分も含む）、長期メモ（`memories/`）。
- **対象:** データを読んだ回の返事だけ。データベース・Web 検索・コードの実行を使った回か、`.csv`・`.json`・`.md` などのファイルを読んだ回。
  - コードの相談で出る数（ポート番号やエラーコード）で、注記が出ないようにするため。
  - 対象は `config/security.yaml` の `grounding` で変えられる。`enabled: false` で止められる。
- **出し方:** 確かめられない数か URL があれば、返事の下に注記を出す。返事は止めない。
  - 注記には、確かめられなかった数と URL、根拠に使ったもの（読んだファイル、問い合わせ・検索・実行の回数）を並べる。
  - URL は、押して開かないように、コードの書式で出す。
  - 注記は、画面と保存した会話にだけ付ける。モデルに渡る会話には入れない（次の返事に持ち込まないため）。
- **記録:** 照合した返事ごとに、監査ログに `grounding` を 1 行出す。件数だけを書く（確かめられなかった数 `numbers`、URL `urls`、案内だけの URL `pointed`、計算で確かめた数 `calculated`）。数や URL そのものは書かない。

注記の例:

```
東京の売上は 777,777 円です。出典: https://example.com/fake-source

---
⚠️ 根拠で確かめられなかった数・URL があります。読んだファイル・データベース・検索・コードの実行の結果と、
これまでの発言の中に見つかりませんでした。モデルの知識か、作り話かもしれません。使う前に確かめてください。
- 数: 777,777
- URL: `https://example.com/fake-source`
- 根拠に使ったもの: `/data/sales.csv`
```

## 分かっている制約

- **数のない作り話は、見つけられません**（「前の四半期より増えました」「当面は横ばいでしょう」）。
- **根拠にある数の取り違えは、見つけられません。** たとえば、大阪の売上（903,500 円）を、東京の売上として書いた場合です。数そのものは根拠にあるので、注記は出ません。
- **利用者が書いた数は、根拠ありとみなします。** 利用者の間違いを、モデルがそのまま使った場合は、注記が出ません。
- **データを読んだ回でも、モデルの知識の数（HTTP の 404 など）には注記が出ます**（空振り）。
- **確かめ先として案内しただけの URL（「〜で確かめてください」「〜で確認できます」）には、注記を出しません。** その URL が本当にあるかは、確かめません。案内の言い方は一覧で決めているので、一覧にない言い方だと、注記が出ます（空振り）。
- **確かめる計算は、表の同じ列の簡単なものだけです。** ほかの計算（割合のもとの数、3 つ以上を選んだ合計）は、合っていても注記が出ます。
- ~~**照合するのは、その回の最後の返事だけです。** ツールを呼ぶ前に話した文は、照合しません。~~ 2026-11-16 に直した。その回に出した返事を、すべて照合する（下の「追記」）。
- ~~**定時実行（画面のない実行）の返事には、注記が付きません。**~~ 2026-11-16 に直した。同じ決まりで照合し、保存する返事に注記を付ける（下の「追記」）。
- **長い会話で、自動の要約で消えたツールの結果は、根拠に入りません。** その結果の数を、あとで書くと、注記が出ることがあります。
- 注記は、返事を流し終えたあとに付くので、少し遅れて出ます。

## 追記（2026-11-16）: 注記の取りこぼしを直した

オーナーの依頼（2026-11-16。「続きをおねがいします」）。2026-11-15 に「使ってみてから決めればよいもの」として挙げていた、注記の取りこぼしの 2 つを直した。どちらも料金はかからない。

**1. ツールを呼ぶ前に話した文も、照合する（画面）**
- **困ること:** 「集計しました。東京は …円です。ファイルに保存します」→ 保存 →「保存しました」のように進むと、数は前の文にしかない。最後の返事だけを照合すると、作り話の数があっても、注記が出ない。
- **直したこと:** その回に出した返事を、すべて照合する。注記は、その回の最後の返事の下に 1 つだけ出す（返事ごとに付けると、1 回の依頼で注記がいくつも出るため）。前の返事は、そのまま残す。
- 返事は 1 つずつ照合する。つなげて読むと、前の返事の終わりの数と、次の返事の始まりの「万」が、1 つの数に読めることがあるため。

**2. 定時実行の返事も、照合する**
- **困ること:** 定時実行は、その場で読む人がいない。結果のチャットを後から開いた人が、作り話の数をそのまま使うおそれがある。
- **直したこと:** 画面と同じ決まりで照合し、確かめられないものがあれば、保存する返事の下に注記を付ける（自動で拒否した操作の知らせのあと。返事のいちばん下）。
- 根拠は、依頼文、ツールの結果（サブエージェントの分も含む）、長期メモ。画面と同じ。
- ツールの呼び出しと結果を集めるため、エージェントの動かし方を `ainvoke` から `astream(stream_mode="updates", subgraphs=True)` に替えた。途中経過を読むだけで、動きは変わらない（確認待ちで止まったときの自動の拒否も、同じ）。
- 定時実行で保存するのは、最後の返事だけ。照合するのも、最後の返事だけにした（保存しない文の数を、注記に並べないため）。

**3. まとめたこと**
- 照合の手順（データを読んだ回か → 照合 → 監査ログ → 注記の文）を `grounding.review()` にまとめ、画面（`ui/app.py`）と定時実行（`schedule_runner.py`）で同じものを使う。片方だけ決まりが変わらないようにするため。
- 長期メモを読む処理も、`grounding.memory_texts()` に移した。
- 監査ログの `grounding` に、`where`（`chat` か `schedule`）と `replies`（照合した返事の数）を足した。

**確かめたこと**
- 単体テスト: `tests/test_schedule_runner.py`（新しく 6 件。本物のエージェントの仕組みと、偽のモデルで動かす）と、`tests/test_grounding.py`（6 件を追加）。全体で 459 件すべて通った。
  - 作り話の数と URL に注記が付く。合っている計算には付かない。データを読まない実行は照合しない。長期メモの数は根拠になる。
  - サブエージェントが読んだファイルも根拠になる（親が `task` しか呼ばなくても照合する）。
  - 自動で拒否した回も照合し、注記は拒否の知らせのあとに付く。
  - わざと元の動きに戻すと、テストが失敗することも確かめた（サブエージェントの分を集めないと 1 件、照合しないと 3 件）。
- 画面と同じ通信での確認（偽のモデル）:
  - `check_grounding.py`（3 項目を追加）: ツールを呼ぶ前に話した文の、根拠にない数と URL が、最後の返事の下の注記に出る。前の返事には注記が付かない。保存した会話でも同じ。
  - `check_schedules.py`（4 項目を追加）: 定時実行でも、根拠にない数と URL に注記が付き、合っている計算には付かない。
  - 画面の回帰確認（`bash tests/e2e/regress.sh`）を、すべて流し直した。16 種類、328 項目がすべて通った（`logs/e2e/20261116-072514` と `-073637`）。
    - 1 回目は、3 種類が「使い捨ての環境を作れなかった」で止まった。確認の中身ではなく、`regress.sh` の準備の待ち方の問題だった（PostgreSQL が初めての起動で一度起動し直す間に、つなぎに行っていた）。待ち方を直して、その 3 種類を流し直した。

**増えた制約**
- **ツールを呼ぶ前に話した文の数にも、注記が出ることがあります**（空振り）。たとえば「上位 100 件を問い合わせます」の 100 です。根拠に入るのはツールの結果で、ツールに渡した値は入らないためです。空振りが多いときは、ツールに渡した値を根拠に入れるかを考えます。
- **定時実行の注記は、結果のチャットを開くまで気づけません。** 知らせ（メールなど）は出しません。
